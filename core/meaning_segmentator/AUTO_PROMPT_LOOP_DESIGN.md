# 의미 분절 프롬프트 자동 생성 루프 — 설계안

> 상태: 기획 단계 (구현 전). 대상 디렉토리: `core/meaning_segmentator/`

## 1. 목표

**입력**: 어떤 언어든 평문 문장 데이터 (`text` 필드만 있는 JSON) + 소스/타깃 언어 코드
**출력**: ① 해당 언어쌍에 최적화된 `<SEG>` 삽입 시스템 프롬프트, ② 그 프롬프트로 분절된 문장 데이터

현행은 사람이 언어마다 프롬프트를 직접 작성한다 (`utils/prompt.txt`의 한국어판 3종, `gpt_seg_en.py`의 영어판). 언어쌍이 늘어날 때마다 사람이 붙어야 하므로 확장이 막힌다. 이 문서는 그 프롬프트 작성 과정을 에이전트 루프로 대체하는 시스템을 설계한다.

## 2. 현행 자산과의 관계

도식의 두 Tool은 이미 구현되어 있다. 새로 만들 것은 평가·피드백·프롬프트 개정 루프다.

| 도식 구성요소 | 현행 코드 | 상태 |
|---|---|---|
| `<SEG>` 넣는 메인 GPT | `utils/gpt_seg_en.py` `mark_segmentation()` | 프롬프트가 하드코딩 상수 → 주입식으로 바꿔야 함 |
| `<SEG>` 없이 전체 번역 (Tool) | `utils/gpt_trans.py` `translate_full()` | 그대로 재사용 |
| `<SEG>`로 따로 번역해 붙이는 Tool | `utils/gpt_trans.py` `translate_segments_with_context()` | 그대로 재사용. 세그먼트 *i* 를 1..*i*-1 컨텍스트만으로 번역 → 실시간 스트리밍 조건을 이미 정확히 재현 |
| 둘을 비교·피드백 주는 agent | 없음 (`utils/comet_eval.py`는 점수만) | 신규 |
| 규칙 제작 agent | 없음 | 신규 |
| 루프 제어 | 없음 | 신규 |

## 3. 설계 원칙

1. **LLM은 세 곳에만** — 언어 프로파일링, 비평(Critic), 프롬프트 개정. 나머지(포맷 검증, 점수 계산, 루프 제어, 재시도)는 전부 결정론적 코드. LLM으로 할 수 있다고 LLM으로 하면 비용과 분산이 같이 늘어난다.
2. **저비용 게이트 먼저** — 포맷 검증(무료) → 세그 밀도(무료) → 번역(중간) → COMET(비쌈) 순으로 통과시킨다. 포맷 위반 프롬프트는 번역 한 번 없이 탈락.
3. **프롬프트가 곧 산출물** — 루프의 최종 결과는 분절된 데이터가 아니라 *프롬프트*다. 데이터는 부산물.
4. **평가 데이터 분리** — 루프가 보는 데이터(train)와 최종 성능 보고용 데이터(test)를 분리하지 않으면 프롬프트가 그 몇십 문장에 과적합된다.

## 4. 핵심 위험: 단일 점수는 "분절 안 함"으로 수렴한다

가장 중요한 설계 지점이다.

`comet_eval.py`는 reference = 전체 번역(`*_full_trans`), hypothesis = 세그 번역 이어붙이기(`*_seg_trans`)로 COMET을 낸다. 이 점수만으로 프롬프트를 최적화하면 **최적해는 "`<SEG>`를 하나도 넣지 않는 프롬프트"**다. 분절이 없으면 seg_trans = full_trans가 되어 COMET이 자동으로 최대가 된다. (현행 `comet_eval.py`가 `<SEG>`가 없는 항목을 아예 제외하는 것도 같은 문제를 가린다.)

분절의 목적은 품질이 아니라 **지연 감소**다. 따라서 목적함수는 반드시 2축이어야 한다.

### 4.1 지표 정의

**품질축 — `Q`**
seg 번역 이어붙임과 full 번역의 의미 유사도. 분절이 없는 항목은 **제외하지 않고 만점(1.0) 처리**한다 (제외하면 "분절 회피"가 무료가 된다).

백엔드는 교체 가능하게 둔다:

| 백엔드 | 내용 | 비고 |
|---|---|---|
| `comet` | COMET (`Unbabel/wmt22-comet-da`), src=원문, mt=seg 번역, ref=full 번역 | 운영 기준 지표. `torch` 필요 |
| `embed` | 게이트웨이 임베딩(`text-embedding-3-large`) 코사인 유사도 | 로컬 ML 의존성 불필요. 현재 구현 기본값 |
| `chrf` | 문자 n-gram F-score | 표면형만 봄 — 보조 지표로만 |

**지연축 — `L`**
스트리밍 지연의 프록시. 각 세그먼트는 문장 끝을 기다리지 않고 나가므로, "그 세그먼트가 나가기까지 통과해야 하는 문장 비율"의 평균으로 정의한다.

```
문장 s, 세그먼트 경계로 나뉜 조각 길이 c_1..c_k (문자 또는 토큰 수, N = Σc_i)
L(s) = (Σ_i (c_1+...+c_i)) / (k · N)
```
`k=1` → `L=1.0` (무분절). `k→∞` → `L→0.5`. **낮을수록 빠름.** 지연 이득 `G = 1 − L ∈ [0, 0.5)`.
보조 지표: 세그먼트 수 `k`, 평균 세그먼트 길이, 문장당 분절률(`<SEG>` 1개 이상인 문장 비율).

**포맷축 — `V`**
결정론적 검증 통과율. 100% 미만이면 그 프롬프트는 즉시 탈락 (점수 계산 자체를 안 함).

### 4.2 목적함수

가중합(`Q - λL`)보다 **제약 최적화**를 권장한다. 논문에 쓰기 좋고 λ 튜닝이 필요 없다.

```
maximize   G = 1 - L                   # 지연 이득 최대화
subject to V = 1.0                     # 포맷 100% 유효
           LCB(Q_seg) ≥ Q_floor        # 분절된 문장의 품질 하한
```

제약 위반 시 동점으로 두면 루프가 방향을 잃으므로, 위반 정도에 비례한 음수를 준다 (사전식 순서):

```
V < 1.0              → -10 + V                    # V를 올리는 방향
n_segmented = 0      → 0                          # 아무것도 안 자름 = 이득 0
LCB < Q_floor        → -1 + (LCB - Q_floor)       # 품질을 올리는 방향
그 외                → G
```

**품질 제약은 분절된 문장에만 건다.** 전 문장 평균을 쓰면 무분절 문장의 `1.0`이 평균을 끌어올려 "적게 분절하면 나쁘게 잘라도 통과"하는 역인센티브가 생긴다. ja 실측: 분절률 0.24에서 전체 `Q = 0.9668`이지만 실제로 분절된 12문장만 보면 `0.8618`로 하한 미달이었다.

**표본 크기를 반영한다.** `Q_seg`를 평균만으로 쓰면 표본이 작을 때 판정이 잡음에 좌우된다 (ja 실측: dev 30문장 중 분절된 것이 4건뿐이라 문장 하나가 `Q_seg`를 0.05 이상 움직였다). 하한 신뢰구간을 쓴다.

```
LCB(Q_seg) = mean(Q_seg) − z · std(Q_seg) / √n_segmented      # z 기본 1.0
```

분절을 적게 하는 프롬프트는 품질 입증 표본도 작아져 이중으로 불리해지므로, 지연축과 같은 방향으로 압력이 걸린다.

**`Q_floor` 캘리브레이션 — 앵커 2개.** 언어쌍·백엔드마다 Q의 절대 스케일이 다르므로 고정 상수는 위험하다.

- **하한 앵커** — 의미를 무시한 기계적 분절(예: 8자마다 절단)의 Q.
- **상한 앵커** — `1.0`이 아니다. 번역기가 결정론적이지 않아 **분절을 전혀 하지 않고 같은 문장을 두 번 번역해도 Q가 1.0이 나오지 않는다.** 이 값이 지표로 도달 가능한 실제 상한이며, 그보다 위를 요구하면 루프는 번역기 잡음을 쫓게 된다.

```
Q_floor = Q_bad + ratio · (Q_ceiling − Q_bad)        # ratio 기본 0.7
```

ja/임베딩 실측: `Q_bad = 0.7341`, `Q_ceiling = 0.9010`, 앵커 간격 `0.1669`, `Q_floor = 0.8509`.
상한을 1.0으로 잘못 두었을 때의 `Q_floor`는 0.9252였고, 이는 **분절을 전혀 하지 않아도 통과하지 못하는 값**이었다.

`anchor_gap`이 좁으면(예: 0.05 미만) 그 백엔드가 분절 품질을 분해하지 못한다는 뜻이므로 백엔드를 바꿔야 한다는 신호다. `baseline.json`에 백엔드별로 기록한다.

### 4.3 지표 타당도 — 백엔드 선택의 실제 기준

**노이즈보다 타당도가 먼저다.** 앵커를 아무리 잘 잡아도, 지표가 "분절이 실제로 일으키는 오류"를 못 잡으면 루프 전체가 무의미하다.

같은 참조 문장에 대해 오류 유형별로 실측한 결과 (ja→ko, 임베딩 `text-embedding-3-large` / 자체 chrF):

| 가설 | 임베딩 | chrF |
|---|---|---|
| 동일 | 1.0000 | 1.0000 |
| 무해한 표기 차이 (장어/뱀장어, 헤이주/병십) | 0.8401 | 0.4597 |
| **부정 뒤집힘** (훔치지 않았다 → 훔쳤다) | **0.9278** | 0.7840 |
| **주체 뒤바뀜** | 0.8460 | 0.8244 |
| **뒷절 누락** | **0.8878** | 0.4920 |
| **지시대상 소실** (그/그것/거기) | 0.4862 | 0.4869 |
| 무관한 문장 | 0.1360 | 0.0411 |

임베딩 코사인은 **의미가 정반대인 번역에 0.9278을 준다** — 상한 앵커(0.9010)보다 높고, 무해한 표기 차이(0.8401)보다도 높다. 순위가 뒤집혀 있으므로 이 백엔드로는 목적함수가 성립하지 않는다. chrF는 절 누락은 잘 잡지만(0.4920) 무해한 변이를 똑같이 벌하고 주체 뒤바뀜을 놓친다.

**결론: `embed`/`chrf`는 진단용 보조 지표이고, 제약에 쓸 수 있는 백엔드는 COMET(또는 오류 유형을 판정하는 LLM 판정자)이다.** 새 백엔드를 붙일 때는 반드시 위 표를 다시 만들어 순위가 정상인지 확인한다 — 앵커 캘리브레이션은 스케일만 맞출 뿐 타당도를 보증하지 않는다.

## 5. 에이전트 구성

LLM 에이전트 3개 + 결정론적 컴포넌트 5개.

### A0. Data Preparer — 결정론적

- 입력 JSON을 `{"id", "text"}` 리스트로 정규화. 기존 `evaluation/*/transcribe/*.json`의 두 구조(KsponSpeech `{"data": [...]}`, DailyTalk `{"0": {"data": [...]}}`)를 모두 흡수.
- 길이·구두점 유무 기준으로 층화 샘플링 후 **train / dev / test** 분할.
  - train (루프가 매 이터레이션 보는 것): 30~50문장. 크면 비용이 선형 증가.
  - dev (프롬프트 후보 채택 판정): 100~150문장. train과 겹치지 않음.
  - test (최종 1회만): 500문장+. 루프는 절대 못 봄.
- 산출: `runs/{src}-{tgt}/{run_id}/data/{train,dev,test}.json`

### A1. Language Profiler Agent — LLM, 실행 1회

사람의 사전지식 없이 시작하기 위한 부트스트랩. train 샘플 일부(20~30문장)를 읽고 언어 특성을 구조화해 초기 프롬프트를 만든다.

**출력 (`language_profile.json`)**
- 소스 언어 식별 + 표기 체계 (띄어쓰기 유무 — zh/ja는 `<SEG>` 좌우 공백 규칙이 달라짐)
- 어순 유형 (SOV/SVO, 핵어 후치 여부). ko/ja처럼 핵어 후치 언어는 분절 경계가 타깃 언어와 잘 맞는지가 다르다
- ASR 출력 특성: 구두점 존재 여부, 필러/간투사 목록 (예: ko `아/어/근데`, en `uh/um/like`), 담화 표지어, 미완성 발화 패턴
- 절 경계 신호: 연결어미(ko `~고/~서/~는데`) vs 접속사(en `but/and then`) 등 언어별 실제 표지
- 타깃 언어 대비 주의점 (대명사 생략 여부, 어순 차이로 분절 시 깨지는 구조)

**출력 (`prompt_v0.txt`)** — 위 프로파일을 채운 초기 시스템 프롬프트. 골격은 언어 무관 템플릿 고정:
`[역할] / [핵심 원칙] / [분절하는 경우] / [절대 분절하지 않는 경우] / [판단 절차] / [출력 규칙] / [예시 — 분절 O] / [예시 — 분절 X]`

이 골격은 현행 `prompt.txt` PROMPT 2가 이미 도달한 형태다. 재발명하지 말고 템플릿으로 고정하고, Prompt Engineer는 **섹션 내용만** 바꾸게 한다 (구조를 흔들면 루프가 발산한다).

### A2. Segmenter — LLM 호출, 에이전트 아님

`gpt_seg_en.py`의 `mark_segmentation()`을 프롬프트 주입형으로 리팩터링. `SYSTEM_PROMPT` 모듈 상수 → 인자.
`temperature=0`. 프롬프트 캐싱 적용 (Anthropic `cache_control`은 이미 코드에 있음 — 시스템 프롬프트가 이터레이션 내에서 고정이므로 캐시 적중률이 매우 높다).

### A3. Format Validator — 결정론적, 하드 게이트

번역 호출 **전에** 돌린다. LLM 없이 순수 문자열 검사:

1. `<SEG>`와 주변 공백을 제거한 결과가 원문과 **정확히 일치** (모델이 텍스트를 고쳐 쓰는 사고가 가장 흔한 실패)
2. 맨 앞/맨 뒤 태그 없음
3. 연속 태그(`<SEG> <SEG>`) 없음
4. 태그 직후 구두점 없음
5. 태그 좌우 공백 (띄어쓰기 없는 언어는 프로파일에 따라 규칙 변경)
6. 설명·라벨 등 군더더기 텍스트 없음

위반 항목은 Critic에게 **위반 유형 + 해당 문장**으로 전달된다. 위반율이 임계(예: 5%)를 넘으면 번역·COMET을 건너뛰고 즉시 "포맷 실패" 피드백만으로 다음 이터레이션.

### A4. Translation Tools — 결정론적 래퍼

- **Full Translator**: `gpt_trans.py` `translate_full()`. 원문 전체를 한 번에 번역 → reference.
- **Streaming Segment Translator**: `gpt_trans.py` `translate_segments_with_context()`. 세그먼트 *i* 는 1..*i*-1 의 원문+번역만 컨텍스트로 받고, 확정된 앞선 번역은 수정 불가 → hypothesis.

두 번역기의 모델·프롬프트는 **루프 전체에서 고정**한다. 여기가 흔들리면 점수 변화가 분절 때문인지 번역 때문인지 구분이 안 된다.
동일 (문장, seg_text) 조합은 캐시에서 재사용 — 이터레이션 간 대부분의 문장은 분절이 안 바뀌므로 캐시 적중률이 높다.

### A5. Scorer — 결정론적

COMET 배치 실행 + `L`·`k`·분절률 집계 → `metrics.json`.
COMET 모델 로드는 프로세스당 1회 (`comet_eval.py`는 매 실행 로드 — 루프에서는 상주 서비스나 배치 재사용 필요).

### A6. Critic Agent — LLM, "둘을 비교하고 피드백 주는 agent"

점수만으로는 프롬프트를 고칠 수 없다. Critic은 **점수가 낮은 이유를 문장 단위로 언어화**하는 역할이다.

**입력** (문장별): 원문 / seg_text / full 번역 / seg별 번역 리스트 / COMET 점수 / 포맷 위반 플래그
**대상**: 전량이 아니라 **COMET 하위 N개 + 포맷 위반 전량 + 분절 0인 문장 일부**(과소분절 탐지용). 비용 절감이자, 잘 된 문장에 대한 무의미한 코멘트 억제.

**출력 (구조화 JSON, 자연어 총평 금지)**
```jsonc
{
  "cases": [{
    "id": "...",
    "error_type": "over_segmentation | under_segmentation | wrong_boundary | format_violation",
    "span": "문제가 된 원문 구간",
    "evidence": "seg 번역에서 실제로 깨진 부분 vs full 번역의 해당 부분",
    "cause": "대명사 지시 대상 소실 | 수식 범위 변경 | 연결어미 뒤 절 독립 불가 | 담화표지 단독 조각 | ...",
    "proposed_rule": "일반화된 규칙 한 줄 (특정 문장이 아니라 규칙으로)",
    "example_pair": {"input": "...", "output": "..."}
  }],
  "aggregate": {
    "dominant_error": "under_segmentation",
    "over_seg_count": 3, "under_seg_count": 11,
    "direction": "더 공격적으로 분절할 것"
  }
}
```

**설계 포인트**
- `proposed_rule`을 반드시 **일반화된 규칙**으로 요구한다. "이 문장에 태그를 넣어라"는 프롬프트 개선에 쓸 수 없다.
- `example_pair`는 그대로 프롬프트의 few-shot 예시가 된다 — Critic이 예시 후보를 생산하는 구조.
- `aggregate.direction`이 과분절/과소분절 방향을 명시해야 Prompt Engineer가 진동하지 않는다.
- Critic은 **점수를 새로 매기지 않는다**. 점수는 COMET이 낸다. Critic이 점수까지 내면 두 개의 서로 안 맞는 점수가 생긴다.

**함정**: reference인 full 번역 자체가 틀렸을 수 있다. 이 경우 Critic이 멀쩡한 분절을 오류로 지목한다. `error_type`에 `reference_suspect`를 추가해 이런 케이스를 배제 가능하게 하고, 이 비율이 높으면 full 번역기 모델을 올려야 한다는 신호로 읽는다.

### A7. Prompt Engineer Agent — LLM, "규칙 제작 agent"

**입력**: 현재 프롬프트 / Critic의 구조화 피드백 / **프롬프트 버전 이력(프롬프트 + 그때의 Q·L·V)** / 언어 프로파일
**출력**: 개정 프롬프트 + `changelog`(무엇을 왜 바꿨는지 한 줄씩)

**제약 (필수)**
- 이터레이션당 **1~2개 섹션만** 수정. 전면 재작성 금지 — 무엇이 점수를 바꿨는지 귀속이 불가능해진다.
- 섹션 골격 고정. 내용만 변경.
- 예시 개수 상한 (예: 분절 O/X 각 15개). 무한 증식하면 프롬프트가 데이터셋 암기로 변한다.
- **이력을 반드시 참조**. 이전에 시도해 점수가 떨어진 변경은 재시도 금지. 이 이력이 없으면 루프가 두 상태 사이에서 무한 진동한다.

### A8. Loop Controller — 결정론적

에이전트가 아니라 오케스트레이터. LLM 판단 없음.

**채택 규칙 (hill climbing)**
1. 새 프롬프트를 **train**에서 실행 → `V` 확인, 실패 시 Critic으로 직행
2. train 점수가 개선되면 **dev**에서 검증
3. dev에서도 목적함수 개선 시에만 `best_prompt` 교체. 아니면 롤백하고 이전 best에서 다른 방향으로 재시도
4. 매 이터레이션 전체 상태를 디스크에 저장 (재개 가능)

**중단 조건 (하나라도 충족)**
- dev 목적함수가 `patience`(예: 3) 이터레이션 연속 미개선
- 최대 이터레이션 도달 (예: 10~15)
- API 예산 소진 (`gpt_seg_en.py`의 `budget_exceeded` 처리 로직 재사용)
- 제약 만족 + 목표 지연 이득 달성

**종료 후**: `best_prompt`로 **test** 1회 실행 → 최종 리포트. 여기서만 test를 본다.

## 8. 비용 설계

이터레이션당 LLM 호출 (train = 40문장, 문장당 평균 3세그 가정):

| 단계 | 호출 수 | 비고 |
|---|---|---|
| Segmenter | 40 | 시스템 프롬프트 캐싱 적용 |
| Full Translator | 40 | 캐시 적중 시 0 (원문 불변 → 사실상 1회차만) |
| Segment Translator | ~120 | 분절이 바뀐 문장만 재계산 |
| Critic | 1~2 | 하위 N개 배치로 한 번에 |
| Prompt Engineer | 1 | |

**절감 수단**
- Full 번역은 원문에만 의존 → 런당 1회면 충분 (캐시 영구)
- 세그 번역 캐시 키 = `hash(seg_text)`. 이터레이션 간 분절이 안 바뀐 문장은 재번역 없음
- COMET은 GPU 배치 1회. 모델 로드를 이터레이션마다 반복하지 말 것
- 모델 티어링: Segmenter/Critic/Prompt Engineer는 상위 모델, 번역 툴은 하위 모델로 고정 가능 (단 런 내에서 절대 바꾸지 말 것)

별표(★)는 ja 실험에서 **실제로 발생한** 것이다.

| 실패 모드 | 증상 | 대응 |
|---|---|---|
| ★ 지표 타당도 붕괴 | 부정 뒤집힘이 최고점을 받음 | §4.3. 백엔드마다 오류 유형별 순위를 실측 |
| ★ 도달 불가능한 상한 | `Q_floor`가 무분절보다 높아 영원히 미달 | §4.2 앵커 2개. 상한은 재번역 실측값 |
| ★ 역인센티브 | 적게 분절하면 나쁘게 잘라도 통과 | 품질 제약을 분절된 문장에만 |
| ★ 소표본 판정 | 분절 문장 4건으로 채택/거부 결정 | `LCB(Q_seg)` |
| ★ 입력이 문장이 아님 | 낭독 호흡 단위·인용부호 미닫힘 조각 → 모델이 빈 출력 | 로더에서 문장 복원 + 정형성 검사. §11의 0단계 |
| ★ Critic 입력 편향 | 망가진 사례만 보여 진단이 "과분절"로 고정, PE 단조 보수화 | 과소분절 사례 고정 쿼터 + `direction`을 사례 카운트가 아니라 **측정 지표**에서 도출 |
| ★ 비평/개정 대상 불일치 | 거부된 후보를 진단해 best에 적용 | 비평 대상 = 개정 대상 = best. best 불변 시 비평 캐시 |
| ★ Reference 비결정성 | 동일 입력 재번역이 Q 0.9273, 최악 0.5866 | 번역 프롬프트에 표기 규범(고유명사·인용부호·절 순서) 고정. 잔여분은 상한 앵커로 흡수 |
| ★ 번역기 원문 반환 | 번역 대신 소스를 그대로 출력 | `looks_untranslated` n-gram 검사 후 1회 재시도 |
| ★ 에이전트 출력 스키마 누락 | Critic이 `aggregate`를 빼먹어 조향 상실 | 집계는 파이썬이 계산. LLM은 사례와 총평만 |
| ★ 에이전트 JSON 파싱 실패 | 원문 인용부호로 이스케이프 깨짐 | `strict=False` + 깨진 출력 되돌려 복구 재시도 |
| 무분절 수렴 | Q는 만점, `k`가 1로 수렴 | §4 2축 목적함수. 분절 0 문장을 제외하지 않음 |
| 프롬프트 진동 | 두 버전 사이 왕복 | Prompt Engineer에 버전 이력 강제 주입, 이터레이션당 1~2섹션 제한 |
| train 과적합 | train 점수↑, dev 점수↓ | dev 채택 게이트, test 완전 격리 |
| 예시 증식 | 프롬프트가 데이터셋 암기로 변질 | 예시 개수 상한, 일반화된 `proposed_rule` 요구 |
| Reference 오염 | full 번역이 틀려 Critic이 오판 | `reference_suspect` 라벨, 비율 높으면 번역 모델 상향 |
| ★ 원문 훼손 | 모델이 텍스트를 고쳐 쓰거나 빈 출력 | Format Validator 규칙 1 + 위반 내용 되돌려 1회 복구, **1차 통과율 별도 보고** |
| 띄어쓰기 없는 언어 | zh/ja에서 공백 규칙이 어긋남 | Language Profile의 표기 체계에 따라 Validator 규칙 분기 |
| ★ 검증기 언어 종속 | 구두점 목록 하드코딩 → es `¿`, hi `।`, th 미대응 | 프로파일의 `trailing_punctuation`, 없으면 유니코드 범주 추정 |
| 비용 폭주 | 예산 소진 | 이터레이션 상한 + 예산 가드 + 이터레이션 단위 재개 |

## 10. 미해결 사항 (결정 필요)

1. **타깃 언어 처리** — 최적 분절은 언어*쌍*에 의존한다 (ko→ja와 ko→en의 좋은 경계가 다르다). 쌍마다 별도 프롬프트를 뽑을지, 아니면 한 소스 언어에 대해 여러 타깃의 점수를 평균해 타깃 무관 프롬프트를 뽑을지. 후자가 운영은 쉽지만 성능은 낮다. **쌍별 분리를 권장**하되 `runs/{src}-{tgt}/` 구조가 이미 양쪽을 수용한다.
2. **Q_floor 값** — 무분절 베이스라인 대비 몇 점까지 품질 손실을 허용할지. 현행 mode2/3/4 평가 결과에서 역산 가능.
3. **런타임 반영 경로** — 뽑힌 프롬프트가 실제 서버(`--gpt-translation` 경로)로 어떻게 들어가는가. 지금 런타임 커밋은 ASR의 SEG 토큰/구두점/VAD 기반이지 GPT 분절이 아니다. 이 루프의 산출물은 (a) 연구용 데이터 생성, (b) 파인튜닝용 SEG 레이블 생성, (c) 런타임 LLM 분절 도입 중 어디로 갈지에 따라 요구 지연 예산이 달라진다.
4. **인간 개입 지점** — 완전 자동으로 돌릴지, `best_prompt` 확정 전에 사람이 한 번 검토할지.

## 11. 구현 순서

ja 실험에서 실패한 순서대로 배치했다. **0~4단계를 건너뛰면 에이전트가 아니라 데이터와 지표 때문에 실패하며, 그 사실을 알아내는 데 대부분의 예산이 든다.** 실제로 6회 런 중 3회가 이 이유로 폐기됐다.

0. **입력이 문장인지 확인한다.** 길이 분포, 문말 부호로 끝나는 비율, 인용부호 짝, 원본 대비 채택 글자수 비율을 찍어본다. 낭독 코퍼스는 호흡 단위로 잘려 있고, 회의록은 화자 턴이 섞여 있다. 문장이 아닌 것을 분절시키면 모델이 빈 출력을 내고 포맷 유효율이 영원히 1.0에 못 간다.
1. Format Validator (LLM 불필요, 즉시 검증 가능). 구두점 규칙은 코드가 아니라 프로파일에서 받는다.
2. Scorer — `L`·분절률·`Q_seg`·`n_segmented`. 무분절 항목을 제외하지 말 것.
3. **지표 타당도 검증 (§4.3).** 오류 유형별 가설 문장을 만들어 순위가 정상인지 본다. 부정 뒤집힘이 무해한 변이보다 높으면 그 백엔드는 쓸 수 없다. **여기서 걸러야 할 것을 안 걸러서 ja 실험 5회 분량이 무효가 됐다.**
4. **앵커 2개 캘리브레이션.** 하한(기계분절)과 상한(무분절 재번역)을 실측한다. 상한이 1.0에서 얼마나 떨어져 있는지가 곧 번역기 비결정성의 크기다.
5. 수동 루프 1회 — 사람이 쓴 프롬프트(`utils/prompt.txt`의 한국어 v1/v2)를 같은 파이프라인에 넣는다. v2는 v1에 `[판단 절차]`와 예시가 추가된 것이므로 **사람이 아는 품질 순서가 이미 정해져 있다.** 지표가 그 순서를 재현하지 못하면 에이전트를 만들기 전에 지표를 고친다. (`eval_prompt.py`가 이 용도다.)
6. Critic 에이전트 — 집계는 파이썬, LLM은 사례와 총평만. 과소분절 사례에 고정 쿼터.
7. Prompt Engineer 에이전트 + 버전 이력 + `direction`별 허용 동작.
8. Loop Controller, 재개·예산 가드. 비평 대상과 개정 대상을 일치시킬 것.
9. Language Profiler (마지막) — 신규 언어 부트스트랩. 앞 단계가 검증된 후에 붙이면 프로파일러 품질을 독립적으로 판단할 수 있다.

실험 기록과 다음 환경에서 할 일은 [autoseg/HANDOFF.md](autoseg/HANDOFF.md) 참조.
