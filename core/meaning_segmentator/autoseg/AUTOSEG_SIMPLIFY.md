# autoseg 간소화 작업 노트

진행 중인 작업을 실시간으로 적는 문서. 브랜치 `autoseg-temp`.

**목표 4가지**
1. 불필요한 파라미터·수치 기준 제거
2. 결정론으로 되는 건 LLM 안 쓰기
3. 전체 구조 간소화 (중복 기능 제거)
4. 에이전트 루프에서 데이터 누출 용납 불가

---

### 파라미터

| 이름 | 정의 | 의미 |
|---|---|---|
| **T** | 조각 당 목표 단어 (글자) 개수 | T 그리드에 따른 지연 변화 |
| **min_gap** | 조각 최소 크기 | 조각 크기의 하한 |
| **t_floor** | 라벨링 밀도 하한 | 최소 몇 단어 (글자)마다 분절이 존재해야하는지 |

띄어쓰기 하는 언어면 단어, 아니면 글자 기준으로 세 파라미터 정의

셋의 관계:

```
1200ms (파라미터)
   × 발화속도 (강제정렬 실측, 단위/초)
   ↓
min_gap  ──▶  t_floor = max(min_gap + 1, ceil(1.25 × min_gap))
                 └──▶  T 격자 = t_floor × {1, 1.5, 2, 3}      최종 곡선
                       루프 격자 = t_floor × {1, 1.5, 3}      비용 때문에 3점만
```

**정하는 건 시간 하나뿐**이고 나머지는 다 따라 나온다.

`min_gap`이 하는 일은 "청자가 알아들을 수 있는 최소 방출량"이라 **문장 길이와
무관**해야 한다. 그래서 시간으로 정하고, 발화속도로 단위 환산만 한다.

| | 발화속도 | 토큰 (어절, 글자) 당 시간 | min_gap |
|---|---|---|---|
| de | 2.43 어절/초 | 0.41초 | 3 어절 |
| en | 2.88 어절/초 | 0.35초 | 3 어절 |
| zh | 4.74 자/초 | 0.21초 | 6 자 |
| ja | 5.77 자/초 | 0.17초 | 7 자 |

발화속도는 앞뒤 무음을 제거한 **발화 구간**으로 잰다. 파라미터 1200ms를 발화속도로 나눠 min_gap이 토큰 단위로 바뀌고, 그 값이 프롬프트에 들어간다.

`t_floor`는 하한 두 개 중 큰 쪽이다.

| | 값 | 어느 단계 | 어기면 |
|---|---|---|---|
| **포화 바닥** | `min_gap + 1` | 자를 때 | 곡선에 같은 점이 겹침 |
| **마킹 한계** | `1.25 × min_gap` | 표시할 때 | 성공할 수 없는 재시도 |

포화 바닥은 유도된다 — `T ≤ min_gap`이면 요청이 용량을 넘어 전부 같은 결과가 된다.

마킹 한계는 실측이다 — 실제 마킹 간격이 de 1.13배 · zh 1.20배 · ja 1.24배다.
물리적 상한은 `min_gap`(1.0배)인데 모델이 그 77~86%만 찍는다. 능력의 벽이 아니라
관측된 행동이라, 더 촘촘히 찍는 게 확인되면 내릴 수 있다.

어절 언어(min_gap 3~4)는 포화 바닥이, 글자 언어(6~8)는 마킹 한계가 결정한다.


### 조각 수 계산

```
조각 수  = max(1, round(문장길이 / T))         chunk_budget()
경계 수  = 조각 수 - 1                         boundaries()
용량     = max(0, 문장길이 // min_gap - 1)     capacity()

남길 경계    = 경계 수(T)                      truncate()
표시 요구량  = min(경계 수(t_floor), 용량)     coverage_need()
```

`boundaries()` 를 두 번 쓴다 — 넣는 T만 다르다.

| | 넣는 T | 나오는 값 | 언제 |
|---|---|---|---|
| **표시** | `t_floor` | 최소 몇 개 찍어라 (표시 요구량) | 분절 1회 |
| **절단** | 격자 `T` | 그중 몇 개 쓸까 | T마다 매번 |

### A0 — 데이터 준비 `data.py`
문장을 읽어서 train/dev/test로 나누고, 코퍼스 특성을 잰다.

```
1. 로더가 파일 읽음 → {id, text} 목록
2. 층화 정렬: 길이 3분위 × 구두점 유무로 묶고 라운드로빈으로 섞음
3. 앞에서부터 test → dev → train 순으로 떼감
   (train을 뒤에 두는 이유: train 크기를 바꿔도 test/dev가 안 밀림)
4. 코퍼스 특성 측정 (measure_profile)
   - 공백 비율 중앙값 > 0.02  →  띄어쓰기 하는 언어
   - 단위 결정: 띄어쓰기 언어면 어절, 아니면 글자
   - 중앙 길이 → min_gap 유도에 씀
   - 구두점 목록: 앞 텍스트에 90% 이상 붙어 나오는 문자만
```

### A2+A3 — 분절과 검증 `pipeline.py` · **LLM + 결정론**

**둘은 한 함수다.** `segment_batch` 가 부르고, 그 안에서 고치고 검사하고 재시도까지 한다.

```
segment_batch(프롬프트, 문장들)
  ├ 캐시 확인            cached()   — 키 만드는 곳도, 빈 값 버리는 곳도 여기 하나
  ├ 배치 호출            6문장씩 묶어서 (사고 토큰 절약).  결과는 pre_map 에 미리 채움
  └ 문장마다 one()
      ├ pre_map 에 없으면 단건 호출
      ├ normalize_tags   표기 자동 수정
      ├ validate         규칙 검사
      └ 위반 남으면 LLM 재시도 1회 (단건으로만)
```

`n` 은 확신도 순위다 (1이 가장 확신). 위치 순서가 아니다.

> **분절·정규화 로직을 고치면 재개·재평가할 런의 `cache/segment.json` 을 지운다** — 캐시엔 정규화 *후* 문자열만 남아 옛 코드 산물이 조용히 섞인다 (새 런은 빈 캐시라 무관).


| | 하는 일 |
|---|---|
| `normalize_tags` | 번호 다시 매기기(**순위 관계 보존**), 맨앞/맨뒤 태그 삭제, 연속 태그를 같은 자리로 합치고 **가장 확신한 번호**를 남기기, 태그 뒤 구두점 옮기기, 좌우 공백 맞추기 |
| `validate` | 원문 훼손 · 태그 개수 부족 · 무번호 태그 — **셋뿐** |
| `_self_check` | 정규화가 자기 약속을 지켰나. 걸리면 프롬프트가 아니라 **정규화 버그** |

**요구 경계 수는 1차 호출에 알려준다.** 종전에는 문장만 보내고 최소 경계 수를
`[Output Rules]` 의 규칙에서 모델이 유도하게 했는데, 그 요건이 실제로는 거의 최대치다:

```
loop405 405문장, coverage_t=4 / min_gap=3
  여유(상한 − 요구) ≤ 1 인 문장   263/405 (65%)
  여유 0 인 문장                    34/405 ( 8%)   ← 합법 위치를 하나도 못 놓친다
```

그래서 1차 위반이 거의 전부 `too_few_tags` 였고(run08 iter0 3/3, run09 iter0 16/16),
재시도 프롬프트가 *"경계 N개 — 최소 M개 필요"* 로 **숫자를 알려주면 그때 통과**했다.
세는 일은 결정론이므로 1차부터 알려주는 것이 맞다 — 재시도가 비용의 23~31%다.

A/B (같은 프롬프트·36문장·batch 6):

```
                1차 통과      위반                       재시도   비용
힌트 없음(종전)  30/36 0.83   too_few 5 + text_mod 1     6콜     $0.2322
힌트 있음(수정)  34/36 0.94   too_few 2                  2콜     $0.1915  (−17%)
```

n=36 단일 시행이라 폭은 못 믿지만 방향은 분명하다 — 재시도가 3분의 1로 줄었다.

**`--seg-reasoning-effort` 가 Letsur 런에서 아무 일도 안 하고 있었다.** 게이트웨이가
`reasoning_effort` 를 **OpenAI 직결일 때만** 실었다 (`if effort and self.is_openai and ...`).
우리 런은 전부 `gw.letsur.ai` 라 파라미터가 한 번도 나간 적이 없다 — run09 를 `low` 로
돌렸는데 사고가 15,330tok/콜 로 `medium` 런(13,876)보다 **오히려 컸던** 이유다.

Letsur 는 이 파라미터를 정상 처리한다 (분절 프롬프트 + 1문장 실측):

```
low 640  /  medium 2,752  /  high 6,464   사고 토큰
```

`response_format` 도 같은 이유로 막혀 있었고 Letsur 에서 정상 동작한다. 둘 다
`is_openai` 조건을 뺐다 — 거부하는 모델은 기존 400 처리(`omit_*`)가 다음 호출부터
알아서 뺀다. 엔드포인트로 미리 막을 일이 아니었다.

고친 뒤 A/B (36문장, batch 6, 재시도 비용 포함):

```
effort     1차 통과   원문 보존   태그 중앙   재시도   비용
medium      0.92      36/36        4          3콜    $0.1998
low         0.50      35/36        4         18콜    $0.1220  (−39%)
minimal     0.11      30/36        3         32콜    $0.0186  (−91%)
```

`minimal` 은 원문 훼손이 6건이라 못 쓴다. `low` 는 39% 싸지만 **1차 통과율이 절반**이라
채점에 들어가는 분절의 상당수가 재시도 산출이 된다 — 점수 영향은 아직 안 쟀다.

### A4 — 절단 `pipeline.py` · **결정론**
노브 T에 맞춰 경계를 골라낸다. 여기가 지연을 정하는 곳.

```
조각 수 = max(1, round_half_up(문장길이 / T))
남길 경계 = 조각수 - 1 개

고르는 법: 순위 1등부터 차례로,
          단 이미 고른 자리·문장 양끝과 min_gap 이상 떨어져야 함
못 채우면 덜 자른다 (억지로 보충 안 함)
```

**보장되는 것**: 조각 개수, 평균 조각 크기(산수), 최소 조각 크기(min_gap)
**보장 안 되는 것**: 최대 조각 크기, 고른 간격

### A5 — 번역 `pipeline.py`
두 종류를 뽑는다.

```
전체 번역  — 문장 통째로. 정답 대용(오라클)으로 씀. 캐시 영구
조각 번역  — 조각 하나씩, 앞 조각들만 보고 번역. 뒤는 절대 안 봄
```

**기본 백엔드는 `local` 이다 — 2026-08-28 에 API 경로가 둘 다 죽었다.**

```
Cloud Translation v2 무료 한도    월 500,000자
루프가 쓰는 양                    이터레이션 1회 약 1,050,000자
                                  (문장 425 × 124자 × 격자3+full × 타깃5)
```

**이터 하나가 무료 한도의 2.1개월치를 쓴다.** 8이터면 840만 자 = 유료 약 $168 로,
LLM 비용($15~20)의 10배다. 새 계정을 파도 한 이터를 못 넘긴다. 실제로 run10 이
iter1 에서 403 `userRateLimitExceeded` 로 멈췄고, 무료 `gtx` 경로도 IP 차단이었다.
**채점(CometKiwi·NLI)이 이미 전부 로컬인데 번역만 유료 API 에 묶여 한도가 차면 루프
전체가 멈추는 구조**였다.

후보 4종을 같은 100문장·5타깃으로 재고 골랐다 (CometKiwi = 루프의 `adequacy`):

```
                adequacy   vs google    ko     ja     zh     es     de
google-v2        0.8712     기준선     .881   .884   .857   .878   .856
madlad400-3b     0.8554    −0.0158     .866   .867   .831   .880   .861
nllb-1.3B        0.8344    −0.0368     .862   .859   .743   .869   .839
nllb-600M        0.8216    −0.0495     .847   .839   .732   .860   .830
m2m100-418M      0.8088    −0.0624     .830   .834   .780   .827   .773
```

**중국어가 갈림길이다** — NLLB 계열은 zh 에서 0.73 으로 무너진다. 그리고 빔서치가
병목이라 greedy + 배치로 바꾸면 madlad 가 **29배 빨라지고 품질은 0.008 만** 떨어진다:

```
madlad-3b greedy   adq 0.8473   40 문장/초   VRAM 8.8GB   →  이터당 번역 ~10분
nllb-1.3B greedy   adq 0.8245  165 문장/초   VRAM 3.7GB
```

지금 Google dev 평가가 15분이므로 **더 빨라진다**. `--translate-backend v2` 로 옛
경로를 계속 쓸 수 있고, 캐시 키와 `translator_id` 에 모델 이름이 들어가 섞이지 않는다.

**로컬은 문맥 번역을 안 쓴다.** Google 경로의 `use_context` 는 앞 조각들을 개행으로
붙여 통째 번역하고 마지막 줄만 취하는데, seq2seq 모델은 개행 구조를 보존하지 않아 그
규약이 성립하지 않는다. 조각을 독립 번역하는 쪽이 **결정론적**이라 쌍체 비교에 오히려
유리하다 — Google 은 분절이 바뀌면 문맥까지 바뀌어 잡음이 낀다.

**Google 접근 경로가 둘이다.**

| | 정체 | 인증 |
|---|---|---|
| `gtx` | 웹 번역 위젯이 쓰는 **비공식** 엔드포인트 | 없음 |
| `v2` | 공식 Cloud Translation **Basic** (API 버전 2) | API 키 |

`GOOGLE_TRANSLATE_API_KEY` 가 있으면 v2, 없으면 gtx. `--translate-backend` 로 고정한다.

gtx 는 인증이 없어 Google 이 구분할 수 있는 게 IP 뿐이라, 이 실험이 6일간 30만 건을
호출해 **IP 단위로 429 를 맞았다**(2026-08-26 현재도 막혀 있다). 429 면 HTML 차단
페이지가 와서 JSON 파싱이 터지고 번역칸만 조용히 빈다. 프로덕션 서버도 같은 이유로
v2 로 옮겼다.

**두 백엔드는 같은 자가 아니다 — 기존 gtx 캐시 18건을 v2 로 재번역해 일치 0/18.**

```
gtx: It's this month, but they say there's an engineering college M-T in March.
v2 : It's February, but I heard the engineering department has an MT in March.
       └ 2월을 "this month" 로 잘못 옮긴 게 gtx
```

그래서 캐시 키와 `translator_id` 에 백엔드가 들어간다. 섞이지는 않지만,
**gtx 로 잰 기존 26개 런의 점수는 v2 런과 비교할 수 없다.**

### A6 — 채점 `metrics.py` · **결정론**
```
adequacy       조각별 번역 품질(참조 없음). 조각 길이로 가중 평균
contradiction  경계마다: (전체번역) vs (그때까지 누적 방출)이 모순인가.
               경계들의 평균. 경계가 없으면 미정의
effective      adequacy × (1 - contradiction)      ← 목적함수
laal_words     지연. 조각 크기로 가중.  **집계에서만 해석** (아래)
consistency    합본 vs 전체번역 양방향 함의의 min   ← 보고용
```

### 확인해야 할 것 — `contradiction` vs `1 − entailment`

조기 방출을 **모순 확률**로 재고 있는데, **함의 확률**로 재는 쪽이 더 나을 수 있다.
오프라인 실측은 전부 그쪽을 가리키는데 표본이 얇아 아직 안 바꿨다.

| | 결과 |
|---|---|
| 관문 최소 여유 | 0.0604 → **0.8377** (14배). contra 가 `premature_scope`·`premature_head` 를 0.10·0.33 으로 겨우 잡는다 |
| 긴 방출 구간 신호 | +0.0115 → **+0.0450** (10-14어절). contra 가 약한 바로 그 구간 |
| 검출력 \|t\| | 0.49 → **0.80** (1.6배). 11회 중 7회에서 우세 |
| 두 척도 순위상관 | +0.923 — 축이 바뀌는 게 아니라 같은 걸 또렷하게 잰다 |
| 채택 결정 | 11회 중 **3회 뒤집힘**(27%). 1회는 부호까지 다름 |

**대가**: `1 − entail` 은 `neutral` 을 벌점에 넣는다. 미완성 조각은 원래 neutral 이 정상이라
설계가 일부러 피한 것이다. 관문에서 `benign_incomplete` 가 0.025~0.041 → 0.086~0.151 로
3~4배 올랐다 (premature 0.99 와는 여전히 6배 이상 벌어져 분리는 유지).

### A7 — 판정자 `agents.py` · **LLM**
**점수를 안 낸다. 사례에 설명만 붙인다.**

```
종전   문장 8개를 뽑아 그 안의 모든 경계를 판정 → premature_rate 라는 비율 생산
       그 비율이 Critic 지표 블록·최종 리포트로 감

지금   contradiction 상위 경계 N개만 판정 → cause / shift / generalized_rule 만
       그 사례에 붙어서 Critic 에게 감. 비율은 만들지 않는다
```

**그래도 남긴 이유.** `contradiction` 은 쌍체 평균으로 뭉개져서 **어느 문장의 어느 자리가
왜 나빴는지가 안 남는다.** Critic 이 규칙을 지어내려면 그 재료가 필요하고, 그건 숫자가 아니라
말이다:

```
cause              polarity not yet settled | wrong participant | modifier scope |
                   head not yet arrived | referent lost
shift              경계를 오른쪽으로 몇 단위, 어떤 말 뒤로 옮겼어야 했나
generalized_rule   이 부류를 막을 규칙 한 줄
```

**`cause` 라벨의 뜻을 한 곳에 뒀다.**

```
polarity not yet settled  부정·양보·의문 표지가 오기 전에 긍정/부정을 확정했다
wrong participant         행위를 엉뚱한 주체·대상·소유자에 붙였다
modifier scope            수식어를 잘못된 핵에, 또는 잘못된 범위로 붙였다
head not yet arrived      기대는 말이 오기 전에 조각이 끝나 번역기가 핵을 추측했다
referent lost             대명사·생략·맨명사를 지시 대상이 오기 전에 내보냈다
other                     위 어디에도 안 맞는 진짜 모순. conflict 에 적는다
```

### A8 — 진단 `agents.py` · **LLM + 결정론**
실패 사례를 모아 말로 정리한다. **무엇을 고칠지는 Critic 이 정한다**

```
Critic 이 받는 것
   실패 사례 (contradiction 상위 + adequacy 하위 + 포맷 위반)
   그중 모순 상위 경계에는 판정자의 cause / shift 가 붙어 있다   ← A7
   지표 전체 + 각 지표의 뜻 + [프롬프트로 움직일 수 있는가]   ← metrics.GLOSSARY
   순위 감사 (어떤 표면 특징을 과신하는가)
   고착 힌트 (직전에 고쳐서 실패한 섹션)
```

**지표는 뜻과 함께 넘긴다 — 그리고 무엇이 프롬프트의 몫인지 표시한다.**
각 항목에 **프롬프트로 움직일 수 있는가**를 붙인다.

```
움직일 수 있음   score · effective · adequacy · contradiction ·
                 rank_lift · missing_boundaries
못 움직임        laal_words (T가 정한다) · chunks_per_sentence (절단기가 고정한다) ·
                 format_pass_rate (남는 건 원문 훼손) · 그 외 진단·보고 지표
```

**`rank_lift` 는 Critic 에게 설명과 함께 넘긴다.** 순위를 무작위로 섞었을 때 `effective` 가 얼마나 떨어지는지 — 경계 **위치**와 분리해 **순위**만 재는 값이다.

```
rank_lift 크다   순위가 실제로 일하고 있다 → [Priority Rules] 를 더 다듬을 가치 있음
rank_lift ≈ 0    순위에 정보가 없다 → [Priority Rules] 를 고쳐봐야 소용없다.
                 문제는 "어디를 찍느냐" 지 "어떻게 줄 세우냐" 가 아니다
```

### A9 — 프롬프트 수정 `agents.py` · **LLM**

### A10 — 압축 `agents.py` · **LLM**
```
compress()   프롬프트가 분량 예산을 넘으면 줄인다.
             `sections_changed` 를 보호 목록으로 받아 **이번에 넣은 변경은 남기고**
             나머지(중복 예시 → 약한 예시 → 같은 말 하는 조건 → 군말) 순으로 깎는다
```

압축해도 예산을 못 맞추면 **다음 후보를 시도한다** (아래). 그래도 다 걸리면 거부한다.

**분량 예산 1.3 → 1.6, 그리고 거부의 대가.** run08 에서 예산이 개정을 연속으로 죽였다:

```
iter2  17,215자 → 압축 16,334  > 예산 14,652  거부
iter3  15,866자 → 압축 14,755  > 예산 14,652  거부 (103자 차)
```

1.3 의 근거("적용된 개정 42건 중앙 1.06 / 발동 2%")가 **편향된 표본**이었다 — 그 42건은
전부 예전 섹션 관문을 통과한 개정이다. 관문을 없애자 산출이 1.4~1.5배가 되어 발동이
연속 100% 가 됐다. 사고 토큰 13.7k 대비 프롬프트가 ~3k 라 1.3→1.6 의 비용 영향은 5% 남짓.

**거부의 대가가 예산보다 나빴다.** 거부되면 프롬프트가 그대로라 다음 이터가 같은 것을
다시 잰다 — `Δ 정확히 0.00000, 변경 0/265`. 둘을 고쳤다:

```
후보 순위대로 재시도   1위가 분량에 걸리면 2·3위를 시도. 이미 채점한 후보라
                       추가 비용은 압축 호출 한 번뿐이다
stale 을 안 올린다     n_changed == 0 은 "개선이 없었다"가 아니라 "측정이 없었다"다.
                       run07 에서 이 가짜 증가가 patience 조기 종료를 앞당겼다
```
