## 1. 한 문단 요약

사람이 언어마다 손으로 쓰던 `<SEG>` 분절 프롬프트를 에이전트 루프로 자동 생성하는 시스템이다. 일본어(ja→ko) 6회 실험에서 **부트스트랩(사람 입력 0으로 언어 프로파일링 → 초기 프롬프트 생성)은 작동**했으나, 임베딩 코사인 지표의 타당도가 붕괴해(§4.1) 개선 루프를 검증하지 못한 채 중단했다. 이후 COMET으로 백엔드를 바꿔 **타당도를 실측 검증하고(§5.1) 한국어→영어 실험을 완주했다(§5.3)**. 결과: **개선 루프의 효과가 처음으로 확인**됐고(dev objective 0.0988 → 0.1032), **지표가 사람이 아는 프롬프트 품질 순서(v2 > v1)를 재현**했다(§5.4). 그 뒤 번역기를 **운영 서버와 같은 Google Translate 로 바꾸고**(§5.6) 결함 4건을 찾아 고쳤다(§5.7) — `max_tokens` 가 thinking 토큰에 잠식돼 조용히 과소분절되던 문제, 경계 진단이 k=2에서 동어반복이던 문제, 지연 지표가 무의미한 조각을 보상하던 문제, `direction` 이 목적함수와 다른 기준을 쓰던 문제. 최종적으로 자동 생성 프롬프트가 **사람이 쓴 프롬프트 3종을 모두 이긴다**(§5.8). 남은 과제는 지표도 포맷도 아니고 **탐색**이다 — train 30문장 과적합, Profiler 초기값 분산, PE 순환(§6).

## 2. 실행 환경

- 모델 게이트웨이: **Letsur AI Gateway** `https://gw.letsur.ai/v1` (OpenAI 호환)
  - 인증: `.env`의 `CLAUDE_API_KEY` (`LETSUR_API_KEY` 환경변수도 인식)
  - 사용 모델: `claude-sonnet-5` (분절·번역·에이전트 전부), `text-embedding-3-large` (embed 백엔드)
  - 응답에 `estimated_cost` 필드가 있어 런 단위 비용 집계에 사용
- 로컬 GPU: **RTX 4090 24GB**. 저장소 루트의 `.venv` (Python 3.12) 에 설치:
  - `torch 2.6.0+cu124`, `unbabel-comet 2.2.7`, `pytorch-lightning 2.6.5`
  - **`setuptools<81` 을 반드시 핀할 것.** `unbabel-comet` 이 끌고 오는 `torchmetrics 0.10.x` 가
    `pkg_resources` 를 import 하는데 setuptools 81+ 에서 제거됐다. 안 하면 `comet` import 자체가
    `ModuleNotFoundError: No module named 'pkg_resources'` 로 죽는다.
  - `Unbabel/wmt22-comet-da` 체크포인트는 HF 캐시에 받아져 있다.
- **`Unbabel/XCOMET-XL` 은 아직 못 쓴다.** HF 게이트 모델이고 계정 `Doo12` 이 라이선스를 수락하지
  않아 `403 Forbidden` 이 난다. 코드는 이미 연결돼 있어(`--quality-backend xcomet`)
  https://huggingface.co/Unbabel/XCOMET-XL 에서 수락만 하면 바로 돌아간다. §5.1 에서 COMET 이
  유일하게 놓친 오류 유형(주체 뒤바뀜)의 후보 해법이다.
- `temperature=0`을 주는데도 동일 입력이 서로 다른 번역을 낸다 (§4.2). 게이트웨이/모델 어느 쪽 원인인지는 미확인.
- 프롬프트 캐싱이 걸리지 않는다 (`cached_tokens: 0`). 입력 토큰 전액 과금.

## 3. 구현 현황

| 파일 | 역할 | LLM |
|---|---|---|
| `gateway.py` | 게이트웨이 클라이언트, 재시도, 비용 집계, 예산 가드, JSON 복구 | — |
| `data.py` | A0 Data Preparer — 정규화, 문장 복원, 층화 분할. 로더 `kokoro`(ja) / `kspon`(ko) | — |
| `pipeline.py` | A2 Segmenter(자가복구 1회) / A3 Format Validator / A4 번역 툴 2종 / 디스크 캐시 | 분절·번역만 |
| `metrics.py` | A5 Scorer — Q 백엔드(COMET·임베딩·chrF), `Q_seg`, LCB, L, 목적함수 | — |
| `agents.py` | A1 Profiler / A6 Critic / A7 Prompt Engineer, 프롬프트 골격 | ● |
| `loop.py` | A8 Loop Controller — 앵커 캘리브레이션, 채택·롤백, 조기 종료, 리포트 | — |
| `eval_prompt.py` | 임의 프롬프트 1개를 루프와 동일 지표로 평가 (사람 프롬프트 비교용) | — |
| `validity_check.py` | 백엔드 타당도 게이트 — 오류 주입 후 순위 확인. **루프보다 먼저 돌린다** | — |
| `validity_cases.json` | 주입할 오류를 고정한 케이스. LLM 생성 아님 — 매 실행 동일 | — |
| `human_prompts/` | 사람 작성 한국어 프롬프트 3종. `ko_human_current` 가 실제 운영본 | — |

품질 백엔드는 `--quality-backend {comet,xcomet,embed,chrf}` 로, 번역기는
`--translator {llm,google}` 로 고른다. 기본값은 `comet` + `llm` 이지만 **운영 조건과
맞추려면 `--translator google` 을 쓴다**(§5.6).
`baseline.json` 에 백엔드와 번역기가 기록되고, 다른 조합으로 같은 런을 이어 돌리면 루프가
경고한다 — 축이 다른 `Q_floor` 를 재사용하면 판정이 무의미해지기 때문이다. `eval_prompt` 는
기준 런에서 둘 다 자동 상속한다.

전부 동작하며 import 검증됨. LLM 판단은 `agents.py` 3곳뿐이고, 포맷 검증·점수·채택 판정·집계·재시도는 결정론적이다.

### 언어 무관성

에이전트 프롬프트 4종(Profiler, Prompt Writer, Critic, Prompt Engineer)에는 특정 언어 지식이 없다. 언어 지식은 **`language_profile.json`을 통해 데이터로만** 들어간다. 검증기의 구두점 목록도 프로파일의 `trailing_punctuation`에서 받고, 없으면 유니코드 범주로 추정한다(es `¿` 는 태그 뒤 허용, hi `।` 인식, th 는 규칙 자동 무력화).

**언어 종속이 남아 있는 곳은 `data.py`의 로더뿐이며 이는 불가피하다** — 파일 포맷과 전처리가 데이터셋 고유다. 새 언어는 `LOADERS`에 로더 하나만 추가하면 되고 프롬프트는 손대지 않는다.

## 4. ja→ko 측정 결과 (임베딩 축, 2026-08-06 이전)

> 이 절의 수치는 전부 **임베딩 코사인 축**이다. COMET 축의 대응 측정은 §5 에 있다.
> §4.1 이 COMET 이관을 촉발한 근거이므로 원본 그대로 남긴다.

### 4.1 지표 타당도 (가장 중요)

같은 참조 문장에 오류를 주입해 백엔드 반응을 실측했다.

기준문: `곤은 뱀장어를 훔치지 않았습니다. 병십이 그것을 강에 돌려보냈습니다.`

| 가설 | 임베딩 | chrF |
|---|---|---|
| 동일 | 1.0000 | 1.0000 |
| 무해한 표기 차이 (장어/뱀장어, 헤이주/병십) | 0.8401 | 0.4597 |
| **부정 뒤집힘** (훔치지 않았다 → 훔쳤다) | **0.9278** | 0.7840 |
| **주체 뒤바뀜** (곤↔병십) | 0.8460 | 0.8244 |
| **뒷절 누락** | **0.8878** | 0.4920 |
| **지시대상 소실** (그/그것/거기) | 0.4862 | 0.4869 |
| 무관한 문장 | 0.1360 | 0.0411 |

ja 앵커: 하한 0.7341 / 상한 0.9010 / `Q_floor` 0.8509.

- 임베딩은 **의미가 정반대인 번역에 상한 앵커보다 높은 점수**를 준다.
- 절이 통째로 누락돼도 `Q_floor`를 통과한다.
- 반대로 무해한 표기 차이는 탈락시킨다.
- 순위가 `부정뒤집힘 > 절누락 > 무해한변이`로 뒤집혀 있다.

**이 상태에서는 목적함수가 성립하지 않는다.** 앵커 캘리브레이션은 스케일만 맞출 뿐 타당도를 보증하지 않는다.

chrF는 절 누락(0.4920)을 잘 잡지만 무해한 변이(0.4597)를 똑같이 벌하고 주체 뒤바뀜(0.8244)을 놓친다. 단독 사용 불가. BLEU는 chrF보다 표면형에 더 가혹하고 ja(무공백)·ko(교착어)에 구조적으로 부적합해 대안이 아니다.

### 4.2 번역기 비결정성

분절을 전혀 하지 않고 **같은 문장을 두 번 번역**한 결과 (ja→ko, n=25, `temperature=0`):

| | 값 |
|---|---|
| 임베딩 Q 평균 | 0.9273 |
| 중앙값 | 0.9516 |
| 최소 | 0.5866 |
| Q < 0.90 비율 | 24% |
| chrF 평균 | 0.7890 |

최악 사례:
```
1회: 밤새도록 좋은 방법이 없을까 생각한 끝에 떠올린 것은 천둥신에 관한 것이었습니다.
2회: 어디 뭔가 좋은 방법이 없을까 하고, 하룻밤 내내 생각한 끝에 떠올린 것이 우레신 이야기였습니다.
```

같은 런에서 고유명사 `兵十`가 **한자 유지 / 병십 / 헤이주** 세 가지로 번역됐고 인용부호도 `「」` 유지와 `""` 변환이 섞였다.

대응으로 세 번역 프롬프트에 표기 규범(고유명사 음역 강제, 인용부호 유지, 절 순서 유지)을 공통으로 못 박았다. 효과: `Q_seg` 0.8760 → 0.8898, 1차 포맷 통과율 0.90 → 0.93. 잔여 변동은 상한 앵커로 흡수한다.

**COMET에서 이 측정을 반드시 다시 하라.** 상한 앵커가 백엔드마다 다르다.

데이터: KokoroSpeech(ja) 낭독 동화 2편. 원본 308행 → 문장 복원 후 168문장(평균 39자).

### 4.4 데이터 한계 (ja)

- 원본 8,319자 중 **6,621자(79.6%)만 채택.** `max_chars` 초과 강제절단분 폐기 정책 때문이며, 버려진 부분이 긴 문장에 편중돼 지연 이득이 과소평가될 수 있다.
- 첫 문장에 제목·저자·장번호가 붙어 있다 (`ごん狐新美南吉一これは、…`).
- 소스가 동화 2편(`ごんぎつね` 119문장, `カウカサスの禿鷹` 49문장)뿐 — **구어 ASR 분포가 아니고 도메인이 사실상 단일.**
- test 50문장 중 38개가 무분절이었다. 모델의 태만이 아니라 head-final 낭독 문어체에서 실제로 자를 데가 적어서일 가능성이 크다.

**ja는 루프 동작 검증용이지 성능 일반화 근거가 아니다.**

## 5. COMET 이관 결과 (2026-08-06)

### 5.1 백엔드 타당도 — 게이트 통과 여부

`validity_check.py` 로 실측했다. 케이스 5건(ja→ko 1, ko→en 4) × 변이 8종. 오류는
`validity_cases.json` 에 고정되어 있어 LLM 생성이 아니고 매 실행 결과가 같다.
ko→en 케이스의 원문은 전부 KsponSpeech `eval_clean_1000.json` 의 실제 발화다.

**무해한 변이를 두 단계로 나눈 것이 이 검사의 핵심이다.** 처음에는 한 단계로 재서
COMET 도 17건 중 10건 위반으로 나왔는데, 원인은 백엔드가 아니라 검사 설계였다.
참조 기반 지표는 표현이 크게 바뀌면(재서술) 의미가 같아도 점수를 깎는 반면 심각한
의미 오류는 오히려 표면형이 참조와 가깝다. 그래서 benign 을 과하게 바꿔 놓으면
**어떤 백엔드든** 순위가 뒤집혀 보인다. §4.1 이 쓴 '무해한 표기 차이'(장어/뱀장어,
헤이주/병십)는 최소 변경 쪽이므로 그 급으로 판정 기준을 맞췄다.

- `benign_minimal` — 동의어·음역 차이. **판정 기준.**
- `benign_paraphrase` — 문장 구조까지 바꾼 재서술. 참고용.

| 변이 | comet | embed | chrf |
|---|---|---|---|
| identical | 1.0000 | 1.0000 | 1.0000 |
| benign_minimal (기준) | 0.9308 | 0.9509 | 0.8620 |
| benign_paraphrase | 0.8414 | 0.8532 | 0.3830 |
| **negation_flip** | 0.8843 | 0.8977 | 0.8081 |
| **role_swap** | 0.9365 | 0.9118 | 0.8678 |
| **clause_omission** | 0.7693 | 0.8597 | 0.5497 |
| **referent_loss** | 0.8660 | 0.9021 | 0.7326 |
| unrelated | 0.3948 | 0.0632 | 0.1216 |
| **순위 위반 / 17** | **1** | 3 | 5 |

**COMET 은 §4.1 의 붕괴를 대부분 해소한다.** 핸드오프가 지정한 게이트인 부정 뒤집힘은
5개 케이스 전부에서 무해한 변이보다 낮게 나온다. 절 누락도 확실히 잡는다(0.7693, 전
변이 중 unrelated 다음으로 낮음). 임베딩이 절 누락(0.8597)을 무해한 변이(0.9509)보다
높게 매기던 문제가 사라졌다.

**남은 blind spot 하나: 주체 뒤바뀜(role_swap).** ja-ko-01 에서 0.9353 > 무해한 변이
0.9224 (+0.0129). 참여자가 둘인 케이스는 ja-ko-01 과 ko-en-01 뿐이고 ko-en-01 은
통과했으므로 표본이 작다. head-final 언어에서 동사가 오기 전에 조각을 커밋하면 실제로
일어날 수 있는 오류 유형이므로 무시하면 안 된다. **XCOMET-XL 이 후보 해법이고,
HF 라이선스 수락만 하면 바로 잴 수 있다(§2).**

chrF 는 단독 사용 불가가 재확인됐다 — 위반 5건, 특히 주체 뒤바뀜(0.8678)을 무해한
변이(0.8620)보다 높게 준다.

산출물: `runs/validity/validity_report.md`, `validity_scores.json`.
`comet`·`chrf` 열은 재실행해도 값이 정확히 같다. `embed` 열만 게이트웨이 임베딩 API의
비결정성으로 소수 4자리에서 1e-4 수준으로 흔들린다 (판정은 바뀌지 않는다).

### 5.7 이후 발견하고 고친 결함 4건

전부 **탐색을 붙이거나 축을 바꾸자** 드러났다. 프롬프트만 바꾸던 동안에는 보이지 않았다.

**① `max_tokens=1024` + thinking 모델 → 빈 출력** (`SEG_MAX_TOKENS = 8192` 로 수정)

게이트웨이의 `claude-sonnet-5` 는 thinking 모델이고 **사고 토큰이 `max_tokens` 에 같이
잡힌다.** 긴 문장은 사고만으로 예산을 소진해 `content` 가 빈 문자열로 돌아왔다
(`finish_reason='length'`, `completion_tokens=1024`). 검증기는 `text_modified` 로 잡고
복구 재시도도 같은 한도라 똑같이 실패한다.

실측 (103자 문장): `max_tokens` 1024 → 빈 출력 / 4096 → 정상(1071 토큰) / 8192 → 정상(918).

**§6-1 에 "포맷 유효율의 일반화"로 적었던 최우선 과제의 정체가 이것이었다.** run01·run02
합쳐 10 이터레이션 동안 Critic 이 `fix output format` 을 지시하고 PE 가 프롬프트를 고쳤지만,
**어떤 프롬프트로도 고칠 수 없는 인프라 문제였다.**

파급이 더 컸다. 검증에 걸린 건 30문장 중 1건뿐이었지만 나머지도 잘린 예산 탓에 조용히
과소분절되고 있었다. 수정 후 같은 조건에서:

| | run02 (버그) | run03 (수정) |
|---|---|---|
| V (1차 통과) | 0.97 (0.93) | **1.00 (1.00)** |
| 분절률 | 0.37 | **0.73** |
| dev objective | 0.1078 | **0.1591** |

`utils/gpt_seg_ko.py:436` 의 claude 경로에도 같은 `max_tokens=1024` 가 있다. 기본 모델이
`claude-haiku-4-5` 라 지금은 안 터지지만, thinking 모델로 바꿔 돌린 기록이 있으면 그 결과는
의심해야 한다.

**② 경계 진단이 k=2 에서 동어반복** (leave-one-out → 배치 비교로 교체)

어느 경계가 범인인지 특정하려고 경계를 하나씩 지워 재측정했는데, **k=2 에서는 유일한 경계를
지우면 무분절이 되고 무분절은 정의상 Q=1.0** 이다. 결과가 항상 `1.0 - Q` 로 고정된다.
분절 문장의 68%가 k=2 였으므로 진단 대부분이 Q 외에 아무 정보도 주지 못했다.

`diagnose_boundaries` 를 **같은 조각 수 + 현재보다 느리지 않은 대안 배치와 비교**하는 방식으로
바꿨다. 비교 대상이 무분절이 아니므로 퇴화하지 않고, "지연을 잃지 않고 품질을 올릴 수
있었는가"라는 원래 질문에 답한다.

**③ L 이 불균등 분절을 보상 — 지표 해킹** (정보량 가중으로 재정의)

②를 고치자 탐색이 곧바로 다음 허점을 찾았다. 기존 `L = Σ 누적_i / (k·N)` 은 조각을
**개수로 평균**해서 1글자 조각과 30어절 조각을 같은 무게로 센다. 그래서 무의미한 조각을
앞에 만들수록 점수가 좋아진다.

```
그 다음에 이거 벤치... <SEG> 그거 하나도...   (의미 분절)   gain 0.2059
그 <SEG> 다음에 이거 벤치... 그거 하나도...   (해킹)       gain 0.4853  ← 1위
```

`그` 하나를 먼저 내보내면 지표상 가장 빠르지만 사용자가 얻는 정보는 0이다.

정보량 가중으로 바꿨다 — 각 조각의 대기시간을 **그 조각이 담은 정보량 비중**으로 가중한다.

```
L = Σ_i (c_i / N) · (누적_i / N)      "정보 1단위가 평균적으로 기다린 시간"
```

같은 해킹이 gain 0.0285 로 무분절과 동등하게 평가된다. **등분할에서는 두 정의가 정확히 같은
값을 주므로**(k=2 → 0.75, k=3 → 0.667) 기존 수치가 통째로 무효가 되지는 않는다. 재채점 결과
gain 이 −0.003 ~ −0.027 내려갔고 **순위는 전부 유지**됐다.

**④ `direction` 이 목적함수와 다른 기준 사용** (평균 → LCB)

목적함수는 LCB(평균의 하한)로 거부하는데 `summarize_critique` 는 평균 `quality_segmented` 를
봤다. 실측에서 Qs 0.8846 > floor 0.8821 이라 "품질 통과"로 판정해
`segment more aggressively` 를 냈지만, 목적함수는 같은 이터레이션을 LCB 0.8647 < floor 로
거부했다. **병목이 품질인데 PE 에게 더 자르라고 지시**하는 상태였다.

**사람 프롬프트는 셋이다.** `ko_human_v1/v2` 는 `utils/prompt.txt` 에서 글자 그대로 추출한
구버전이고, **`ko_human_current` 가 실제 운영본**(`utils/gpt_seg_ko.py` 의 `SYSTEM_PROMPT`)이다.
셋 다 ko→en 용이다. current 는 컨텍스트 번역기를 명시적으로 전제하고 "적극적으로 분절하라"고
지시하므로 자동 프롬프트와 목표가 같은 진짜 경쟁자다.

읽는 법: 세 사람 프롬프트가 곡선의 양 끝에 있다.

```
분절 적게 ←──────────────────────────────→ 분절 많이
v2(0.33)   v1(0.39)   run05(0.48)  run03(0.57)   current(0.73)
LCB +0.816  +0.800     +0.746      +0.703        +0.614
gain 0.0770 0.0927     0.1169      0.1383        0.1935
                                    ↑ floor +0.700
```

- v1/v2 — 품질 여유를 +0.10 이상 남기고 지연을 못 번다.
- current — gain 이 전체 1위지만 **LCB 가 floor 를 0.034 밑돌아 탈락**한다.
- 자동 run03 — 경계에 여유 0.003 으로 붙는다. 제약형 목적함수의 최적에 가장 가깝다.

**자동이 사람 셋을 모두 이긴다.** 다만 조건은 대등하지 않다 — 자동 프롬프트는 이 데이터의
train/dev 로 튜닝됐고 사람 것은 아니다. 정확히는 *"이 언어쌍·데이터·번역기에 맞춰 측정하며
튜닝한 프롬프트가, 측정 없이 손으로 쓴 프롬프트보다 낫다"* 이고, 그것이 자동화의 가치다.
프롬프트 작성 능력 자체의 우열은 아니다.

### 5.9 품질 꼬리가 제약되지 않는다 (미해결)

목적함수의 품질 제약은 **평균(LCB)에만** 걸려 있어 개별 문장의 붕괴를 막지 못한다.

| 프롬프트 | 평균 Qs | p10 | **min** | pos(min) | Q<0.70 |
|---|---|---|---|---|---|
| 자동 run03 | 0.8947 | 0.7716 | 0.6316 | **+0.063** | 2 |
| 사람 current | 0.8603 | 0.7122 | 0.4940 | **−0.288** | 6 |
| 사람 v1 | 0.9331 | 0.8168 | 0.7674 | +0.408 | 0 |
| 사람 v2 | 0.9401 | 0.8338 | 0.7716 | +0.419 | 0 |

자동 run03 은 제약을 통과하면서 최악 문장이 기계분절(pos 0)과 거의 같다. current 는
**기계분절보다 더 망가진 문장**이 있다(pos −0.288).

`LCB` 는 **표본 수**에 대한 방어(적게 자르고 숨는 것 방지)이지 꼬리 방어가 아니다. 실측상
n 을 36 → 10 으로 줄여도 페널티는 0.0110 → 0.0208 밖에 안 늘어 구속력이 없다.

꼬리 제약을 넣으면 gain 이 떨어지지만 **생각보다 싸다.** 문제 문장을 무분절로 되돌리는
최악 가정에서:

| 기준 | 해당 | gain | 손실 |
|---|---|---|---|
| Q<0.607 (기계분절 이하) | 0건 | 0.1654 | 0% |
| Q<0.70 | 2건 | 0.1592 | −3.7% |
| Q<0.75 | 3건 | 0.1566 | −5.3% |

붕괴 문장이 적고 지연 기여도 작다(하위 10% 5건이 전체 gain 의 8.3%). 실제로는 되돌리는
대신 경계를 옮기면 되므로 손실은 더 작다.

**k 와 Q 는 무관하다** (상관계수 +0.017). 최악 문장이 k=2 이고 k=4 구간이 평균 0.8717 로
오히려 안정적이다. 붕괴는 "많이 잘라서"가 아니라 **"잘못된 자리에서 잘라서"** 생긴다.

권고: `min ≥ 하한앵커`(파국 방지) + `p10 ≥ pos +0.40`(꼬리 두께). 둘 다 이미 `Metrics` 에
계산돼 있어 목적함수 3줄이면 된다.

### 5.10 배치 진단의 효과는 아직 미확인

`diagnose_boundaries` 를 붙인 run05 가 run03 에 졌다 (obj 0.1169 vs 0.1383). 원인을 분리할
수 없다:

1. **Profiler 가 비결정론적이라 초기 프롬프트가 매 런 다르다.** run03 iter 0 은 분절률 0.73,
   run05 는 0.50 에서 출발했고 4 이터레이션으로 그 격차를 못 메웠다. **진단 유무보다 초기값
   복권이 더 크게 작용한다.**
2. **train 30문장 과적합.** run05 iter 2 는 train obj 0.1469(최고)인데 dev 0.1081 로 하락했다.
3. **PE 순환.** run05 iter 4 의 지표가 iter 1 과 소수점까지 동일하다 — 같은 프롬프트로
   되돌아갔다. 미채택 이력을 참조하라는 규칙(PE 제약 5번)이 안 먹었다.
4. 진단 자체는 정상 작동했다. run05 iter 0 에서 4건 전부 `개수 문제`로 판정했고(최대 headroom
   +0.0384, 임계 0.05 미달), PE 는 그에 따라 분절을 줄였다. 진단이 틀린 게 아니라 **그 프롬프트에
   개선 여지가 없다고 정직하게 답한 것**이다.

효과를 재려면 **초기 프롬프트를 고정한 A/B** 가 필요하다 (`iter_00/prompt.txt` 를 복사해
두면 루프가 재사용한다).

## 6. 다음에 할 일 (우선순위 순)

> 이전 1순위였던 "포맷 유효율의 일반화"는 §5.7-① 로 **해결**됐다 — 프롬프트 문제가 아니라
> `max_tokens` 버그였다. 이전 7번(`direction` 기준 불일치)도 §5.7-④ 로 해결됐다.

1. **train 표본을 늘려라 (30 → 60~100).** 실측된 문제 중 가장 직접적이다. run05 iter 2 가
   train obj 0.1469(최고)인데 dev 0.1081 로 떨어졌다. 30문장으로는 dev 로 전이되는 신호가
   안 잡힌다. 번역이 Google 이면 무료이므로 비용은 분절·에이전트 호출만 늘어난다.
2. **초기 프롬프트를 고정한 A/B 로 진단 효과를 재라.** Profiler 가 비결정론적이라 런마다
   출발점이 크게 달라지고(분절률 0.30~0.73), 그 분산이 기능 차이를 덮는다(§5.10).
   `iter_00/prompt.txt` 를 복사해 두면 루프가 재사용한다. **이걸 하기 전에는 어떤 기능
   변경도 효과를 주장할 수 없다.**
3. **품질 꼬리 제약 추가** (§5.9). `min ≥ 하한앵커` + `p10 ≥ pos +0.40`. gain 손실 4~5%로
   Q<0.70 문장을 없앤다. 지표는 이미 `Metrics` 에 있다.
4. **PE 순환 차단.** run05 iter 4 가 iter 1 프롬프트로 되돌아갔다(지표 완전 일치). 미채택
   이력 참조 규칙이 안 먹는다. 개정본 해시를 기록해 중복을 코드로 거부하거나, 한
   이터레이션에 후보 여러 개를 생성해 dev 로 고르는 쪽이 낫다.
5. **XCOMET-XL 로 role_swap 재측정.** HF 라이선스 수락만 필요하다(§2). COMET 이 유일하게
   놓친 오류 유형이다.
6. **런타임 반영 경로 미정.** 서버 커밋은 ASR 의 SEG 토큰·구두점·VAD 기반이지 GPT 분절이
   아니다. 산출물이 (a) 연구용 데이터, (b) 파인튜닝 SEG 레이블, (c) 런타임 LLM 분절 중
   어디로 가는지에 따라 요구 지연 예산이 달라진다. 다만 **번역기를 Google 로 맞춰 두면
   운영 조건과 일치**하므로 (c) 로 갈 때 측정이 그대로 옮겨 붙는다.
7. **ja→ko 재실행.** 현재 ja 수치는 임베딩 축 + `max_tokens` 버그 + 구 L 로 측정된 것이라
   전부 신뢰할 수 없다. `--translator google --quality-backend comet` 으로 다시 돌려야
   ko→en 과 비교 가능해진다.
8. **타깃 언어별 프롬프트 분리 여부.** 최적 분절은 언어쌍에 의존한다. `runs/{pair}/` 구조가
   양쪽을 수용하나 정책은 미정.
