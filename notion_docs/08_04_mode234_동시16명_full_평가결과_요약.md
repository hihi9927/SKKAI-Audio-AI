### 해석

**WER과 지연이 정확히 트레이드오프 관계.** mode3이 WER 5.74%로 mode2의 절반 수준이지만 FSL은 4.5배, FTL은 3.8배 느리다. 커밋당 토큰 수(5.12 vs 13.39)가 원인을 그대로 보여준다 — mode2는 2초 청크를 문장 경계와 무관하게 잘라 커밋하므로 단어가 토막나고, mode3은 문장이 확정될 때까지 기다려 문맥이 온전한 상태로 커밋된다.

**mode2의 지연 안정성이 두드러진다.** FSL p99가 0.0952s로 p50(0.0642s)과 거의 차이가 없다. 반면 mode3은 p99 1.65s, mode4는 p99 3.06s로 꼬리가 길다. 실시간성이 중요한 구간에서는 mode2의 예측 가능성이 강점.

**~~mode4의 WER 13.47%는 모델 불일치에 따른 예상 범위.~~** ← **이 해석은 틀렸다. 아래 "mode4 재측정" 절 참조.** 원인은 모델의 영어 성능이 아니라 반복 루프가 finish 커밋으로 새어나간 파이프라인 결함이었고, 같은 조건에서 영어 파인튜닝 모델로 재측정하니 WER 4.55%가 나왔다.

### mode3의 finish 33건은 원인이 다르다

mode3은 반복이 아니라 **dot 확정 게이트가 성립하지 못한 경우**다. 모델이 미완성 가설의 프론티어에 항상 임시 마침표를 붙이는데:

### 코드 수정 — finish 경로 반복 방어

`Qwen3-ASR/examples/streaming_websocket_server.py`에 `_collapse_repetition()`을 추가하고 `flush_uncommitted`가 커밋 직전에 호출하도록 했다. en 모델에서는 루프가 안 생겨 증상이 없지만, 결함 자체는 모델과 무관하게 남아 있으므로 방어한다.

- **주기 n의 반복**을 찾는다. 연속-동일 문장만 접으면 폭주 9건 중 4건(`"A. B. A. B. …"` 형태의 2문장 사이클)이 안 잡힌다. 긴 주기부터 시도해 `"A B A B"`를 A·B 각각의 1주기 반복으로 오판하지 않게 했다.
- **`max_repeats=2`** — 실제 발화에도 같은 문장 2회 반복이 있다(`3005-163389-0001` 정답이 "TEAR DOWN THE FENCE TEAR DOWN THE FENCE"). 2회까지 보존하면 정상 반복은 안 건드리고 루프만 자른다.

## 🔁 mode3 중복 커밋 제거 — 같은 날 추가 작업

### 왜 팠나

mode4가 mode3를 이기는 게 이상했다. 문장이 확정될 때까지 기다리는 dot-commit이 문맥상 유리한데 WER은 밀렸다. S/I/D로 쪼개 보니 **인식 능력은 실제로 mode3이 더 좋았다**:

| | WER | 치환(S) | 삽입(I) | 삭제(D) |
|---|---|---|---|---|
| mode3 (dot, baseline) | 5.81% | **3.03%** | **2.34%** | 0.44% |
| mode4 (seg, en-silence-c80) | 4.76% | 3.60% | 0.62% | 0.54% |

치환률 3.03% vs 3.60%로 mode3 우위. 뒤집힌 건 삽입 하나 때문이었다.

### 원인 — 같은 문장이 철자만 바뀌어 여러 번 커밋됨

`7105-2340-0005` (참조 63단어 → 가설 143단어):

```
dot  "Alfred Fichencourt had covered himself with honors in the course of Marlborough's campai..."
dot  "Alfred Fychencote had covered himself with honors in the course of Marlborough's campaig..."
dot  "Alfred Pichenot  had covered himself with honors in the course of Marlborough's campaigns"
```

`7975-280057-0002`도 같은 패턴 (`Beresheba` → `Bertha` → `Brusheba`).

dot 확정 게이트가 문장을 커밋한 뒤 모델이 재디코딩하며 **고유명사 철자만 바꿔** 같은 문장을 다시 내놓는다. 기존 `cross-dedup`은 `_asr_key`(공백·대소문자·끝 구두점만 정규화한 뒤 **완전 일치**)로 판정하므로 철자가 달라지면 새 문장으로 보고 또 커밋한다. mode3 총 삽입 1,224단어 중 **911단어(74%)** 가 이 재방출이었다.

커밋 경계에서 단어 몇 개 겹치는 흔한 문제(36단어, 0.07%)는 두 모드 다 거의 없었다 — 문장 통째 재방출이 원인.

### 수정 — 두 군데였다

**v1. `_cross_dup_match()`** — 커밋 루프(`_process_slot_updates`)의 cross-dedup을 유사도 판정으로 보완.
- 6단어 미만은 완전 일치만 본다. `He said yes.` / `He said no.`처럼 실제로 다른 짧은 문장이 유사도만으로는 구분되지 않는다.
- 임계 0.85 (full 2939 튜닝값). 0.95면 철자 변형을 놓치고, 최소 단어수를 10으로 올리면 짧은 재방출을 놓친다.
- `always_commit`(mode2)은 커밋 단위가 문장이 아니라 청크라 제외 — 기존 `seg-boundary-dedup`과 같은 판단.

**v2. `_drop_already_committed()`** — `flush_uncommitted`가 커밋 직전 문장 단위로 같은 판정을 적용.

v1만으로는 절반밖에 안 잡혔다. `flush_uncommitted`가 `committed_asr_set`을 **아예 보지 않아서**, dot으로 커밋된 문장을 finish flush가 그대로 재방출하고 있었다:

```
3538-142836-0017:  dot    'In all the operations for preserve making, ...'
                   finish 'In all the operations for preserve making, ...'   ← 같은 문장
```

**finish 경로가 스트리밍 커밋 경로의 가드를 우회하는 패턴이 오늘만 세 번째다** — 반복 루프 누수(`_collapse_repetition`), 재방출 누수(`_drop_already_committed`), 그리고 mode3 finish 33건. `flush_uncommitted`가 커밋 루프의 방어를 하나도 공유하지 않는 구조적 문제.

## 🔁 커밋 가드 단일 파이프라인화 — 같은 날 추가 작업

### 왜 했나

하루에 같은 종류의 결함이 세 번 나왔다. 전부 **경로 B(flush)가 경로 A(커밋 루프)의 가드를 안 거치는** 문제였다.

| | 경로 A가 한 일 | 경로 B가 한 일 |
|---|---|---|
| 반복 루프 (mode4-ko) | `rep-dedup` 8,047회 발동해 반복 스킵 | 스킵된 반복 전체를 finish로 덤프 (545토큰) |
| 재방출 (mode3) | `cross-dedup`으로 완전일치는 스킵 | 이미 커밋된 문장을 finish로 재방출 |
| finish 33건 (mode3) | dot 확정 게이트가 "아직 확정 못 함" 판정 | 확정 안 된 걸 finish로 그냥 내보냄 |

경로 A에서 스킵된 텍스트는 **커밋만 안 될 뿐 `state.text`에 그대로 남는다** (`committed_len`이 전진하지 않으므로). 스트림이 끝나면 B가 그 누적분을 통째로 내보낸다. 즉 A의 가드는 "이 문장은 출력에 없다"를 보장하지 못하고 **"A를 통해서는 안 나간다"만 보장**한다.

수정 전 가드 분포:

| 가드 | 경로 A | 경로 B |
|---|---|---|
| `rep-dedup` | ✅ | ❌ |
| `seg-boundary-dedup` | ✅ | ❌ |
| `cross-dedup` | ✅ | ❌ |
| `dot-suffix-dedup` | ✅ | ✅ |
| `timeout-skip` / `flush-skip` | ❌ | ✅ |

### 수정

`_commit_skip_reason()` 하나가 모든 가드를 갖고, 두 경로가 이걸 호출한다.

```
경로 A  _process_slot_updates
          ├─ extract 시점 → _commit_skip_reason(stage="extract")
          └─ commit  시점 → _commit_skip_reason(stage="commit")
경로 B  flush_uncommitted
          └─ _apply_commit_guards → 문장 단위로 _commit_skip_reason(stage="flush")
```

A의 판정 시점이 둘로 나뉘는 건 구조상 어쩔 수 없다 — 문장을 뽑는 시점(extract)과 커서를 확정하는 시점(commit)이 다르고, 후자는 `flush_lock` 안에서 일어난다. 그래서 시점은 `stage`로 구분하되 **가드 자체는 한 벌만** 둔다.

`_GUARD_STAGES`가 "어떤 가드가 어느 경로에서 도는가"의 단일 출처다:

| 가드 | extract | commit | flush |
|---|---|---|---|
| `rep-dedup` | ✅ | | |
| `seg-boundary-dedup` | ✅ | | |
| `dot-suffix-dedup` | ✅ | | |
| `cross-dedup` | | ✅ | ✅ |
| `cross-dedup-fuzzy` | | ✅ | ✅ |

**빈칸은 여전히 있다.** 다만 이제는 사고가 아니라 근거를 코드에 적어둔 판단이다:

- `rep-dedup` — 같은 관심사를 `_collapse_repetition`이 처리하고, 그쪽은 정상 발화의 2회 반복을 일부러 보존한다. flush에서 1회로 깎으면 그게 깨진다.
- `seg-boundary-dedup` — 경계 단어 하나로 문장 전체를 버리는 공격적인 가드라, 한 문장이 긴 flush에서 오발동하면 손실이 크다.
- `dot-suffix-dedup` — flush에는 누적분 앞머리를 잘라내는 자체 prefix-strip 블록이 따로 있어 대상이 다르다.

**이게 실질적 이득이다.** 전에는 "flush에 가드가 없다"는 사실 자체가 코드에 흩어져 보이지 않았다. 이제 새 가드를 추가하려면 이 표에 적용 시점을 명시해야 하고, 한쪽에만 넣는 실수가 리뷰에서 드러난다.
