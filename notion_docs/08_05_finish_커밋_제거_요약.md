## 1. 출발점 — finish는 왜 남아 있었나

8/4 mode3 full(dedup 수정본)에서 finish 59파일. 그중 **13건은 파일 전체가 finish 한 덩어리**로 나갔다.

```
6128-63241-0006   오디오 21.3s → FTL 26.76s   (전체가 커밋 1개)
8461-281231-0024  오디오 20.2s → FTL 25.71s
2609-156975-0004  오디오 18.1s → FTL 23.63s
```

21초 발화가 26.8초 뒤에 한 덩어리로 나온다. 실시간 자막으로는 못 쓰는 동작.

**dot이 안 찍혀서가 아니다.** 13건 전부 마침표로 끝나고, 로그에도 `DOT-PENDING`이 매 청크 갱신된다. 모델이 미완성 가설 끝에 **임시 마침표**를 붙이는데 문장이 계속 자라 확정이 안 되는 것:

```
chunk  8  '...sorrowing deeply for his loss.'                       → DOT-PENDING
chunk  9  '...for his lost friend, the Lord of Conings.'            → revised
chunk 10  '...and he and his followers.'                            → revised
   ... 오디오 끝까지 반복
```

확정 게이트 3규칙이 전부 불발한다:

| 규칙 | 조건 | 불발 이유 |
|---|---|---|
| 1 context | 마침표 뒤 토큰 수 > 롤백 창 | 마침표가 항상 맨 끝이라 뒤가 빔 |
| 2 stable | 직전 청크에도 같은 경계가 있음 | 문장이 자라며 경계 키가 계속 바뀜 |
| 3 stall | 미커밋 토큰 수 정체 | 계속 증가 중 |

13건 중 12건이 **내부 문장경계가 없는 run-on 문장**. 확정 가능한 지점이 발화 끝까지 하나도 없다.

## 2. trailing silence 실험 — 메커니즘 확인, 해법은 아님

`TESTING_MANUAL`에 "5500ms에서 0.11초 모자라 finish, 8000ms에서 dot 확정" 실측이 있었다. 확정 판정은 누적 오디오가 `chunk_size_sec`(2.0s) 배수에 도달할 때만 도므로, 무음 청크를 몇 개 더 넘겨야 문장이 안 자라는 걸 확인하고 규칙 2/3이 성립한다.

**paper 스크립트는 5500을 쓰고 있어 문서 권고(8000)와 어긋나 있었다.**

동일 조건 A/B(러너·파일목록 고정, trailing만 변경):

| | finish파일 | 전체한방 | WER | FTL평균 | FTL최대 |
|---|---|---|---|---|---|
| trailing 5500 | 40 | 5 | 12.53% | 8.55s | 25.71s |
| trailing 8000 | 33 | 3 | 12.20% | 8.84s | **29.27s** |

**메커니즘은 맞지만 해법은 아니다.** finish를 3분의 1도 못 줄이면서 지연이 늘고, 무엇보다 trailing silence는 **평가 하네스가 붙이는 무음**이다. 실제 모바일 클라이언트는 발화 끝에 8초 무음을 보내지 않는다.

> 처음엔 59→33, 13→3으로 보고했다가 정정했다. 그 비교는 동시(full) vs 순차(필터링)라 러너 차이가 섞여 있었고, 통제하니 40→33 · 5→3이었다. (아래 "검증 방법 함정" 참조)

## 3. 수정 5단계

프로덕션에 실제로 듣는 방식 = **서버가 스트림 종료 시 내부적으로 확정 판정을 한 번 더 도는 것.** 클라이언트 무음 패딩에 의존하지 않는다.

### ① 규칙 4 — 스트림 종료를 확정 근거로

단순히 청크 판정을 한 번 더 부르는 것으로는 안 된다. 규칙 2/3이 **오디오 증가**를 조건으로 걸기 때문(`_accum_now > _prev_accum`, `_accum_c > stall_accum`). finish 시점엔 오디오가 안 늘어 원천적으로 불성립.

그래서 종료 자체를 근거로 삼는 규칙을 추가했다. `finish_streaming()`이 `flush_uncommitted`로 가기 전에 `_process_slot_updates(final=True)`를 한 번 태운다.

```python
elif final:
    # 오디오가 더 오지 않는다 = 발화가 끝났다. 더 유예할 이유 없음
```

처음엔 규칙 3처럼 `and not after.strip()`(마지막 경계만)로 제한했다가 **보류된 모든 경계**로 확대했다. 커밋 루프는 앞 경계가 미확정이면 거기서 `break`라 뒤까지 가지 못하는데, 정작 막힌 게 중간 경계였다.

커밋 시점이 어차피 finish가 나가던 그 순간이라 **지연 손해가 없다** — trailing 8000이 FTL을 악화시킨 것과 대비된다.

### ② flush 문장 분할

약어(`Mr.`/`S. J.`) 때문에 `DOT_COMMIT_BOUNDARY_RE`가 경계를 못 잡는 문장은 여전히 통째로 flush에 온다. 커밋 사유는 finish로 두되 덩어리만 나눈다.

**분할은 반드시 정책 정규식으로.** 순진하게 `[.!?]`로 자르면 약어에서 깨진다:

```
naive : 'No doubt, returned Mr.' + 'Lilburn.' + 'But, if thy...'   ← 쓰레기
policy: 'No doubt, returned Mr. Lilburn.' + 'But, if thy...'        ← 정상
```

번역도 문장 단위로 돌아 품질에 유리하다. 모드2는 커밋 단위가 청크라 제외.

### ③ 접두사 스트립

재디코딩이 앞 문장은 그대로 두고 뒤를 이어붙여 다시 내놓는 케이스:

```
커밋됨: 'Before the big wind ... his Irish compatriot.'
재방출: 'Before the big wind ... his Irish compatriot, slightly laughed the Colonel.'
```

길이가 달라 유사도 dedup을 빠져나가고, 통째로 버리면 뒤의 새 내용까지 잃는다. **겹치는 앞부분만 잘라 뒤만 커밋**한다.

규칙 4가 유예를 풀면서 이 케이스가 늘어(1건 → 2건) 도입했다. 8/4 문서에 "접두사 중복 잔존"으로 남겨뒀던 그 결함.

> **커서 안전성**: 커밋 지점 3곳 중 vad 경로만 커서 추적에 `sentence_display`를 쓴다. 처음에 커서 계산 **앞**에 넣었다가 커서가 깨질 것을 발견하고 **커서 확정 후**로 옮겼다. 일반 경로는 `sentence_raw` 기준이라 안전.

### ④ 커밋 단계 스킵 시 커서 전진

스킵은 "안 내보낸다"이지 "원문에서 소비 안 했다"가 아니다. 커서를 그대로 두면 다음 문장의 `startswith` 검사가 실패해 `break`로 빠지고, **뒤 문장 전부가 인질**이 되어 finish flush로 흘러간다.

```
1998-29455-0019: 중복 'Ha!' 1건이 뒤의 'You are.' 2문장을 finish로 끌고 감
```

이 수정이 가장 컸다 — finish 31 → 1, dot 커밋 94 → 128개.

### ⑤ 커서 재동기화 — 시도했다가 **되돌림**

④는 **커밋 단계** 스킵만 커버한다. **추출 단계**(`rep-dedup` 등)에서 스킵된 문장은 `sentences_to_commit`에 안 들어가 커서를 밀 기회 자체가 없어 갭이 남는다.

```
7902-96592-0032: 'Ha!' 3연속 중 rep-dedup이 하나를 걸러
                 뒤의 'Laughed the boy jeeringly.'가 매칭 실패 → finish
```

`startswith` 실패 시 `break` 대신 `tail.find(sentence_raw)`로 재동기화하게 했다. finish는 0이 됐지만 **커밋 순서가 뒤집혔다**:

```
   dot 'Ha!' / dot 'Laughed the boy jeeringly.' / dot 'Ha!'
                    ^^^^^^^^^^^^^^^^^^^^^^^^^^^ 원문 순서와 다름
```

`find()`가 **가장 앞 occurrence**를 잡아 같은 문구가 반복되면 엉뚱한 자리로 점프한다. 실시간 자막에서 순서 뒤바뀜은 WER보다 체감이 나쁘고, `segmentId`·`audioStartSec`도 순서 기준이라 타이밍 지표가 어긋난다.

"갭에 완결된 문장이 있으면 재동기화 포기" 가드도 넣어봤으나, ⑥으로 갭의 근본 원인을 없애자 **발동 자체가 0회**가 되어 전부 제거했다. 순서 뒤집힘 위험만 남기고 얻는 게 없다.

### ⑥ rep-dedup 재검토 — 갭의 근본 원인

⑤에서 다룬 갭은 `rep-dedup`이 만든 것이다. 그런데 **이 가드가 지금도 값을 하는지**를 실측해 보니:

| 실행 | 모델 | rep-dedup 발동 |
|---|---|---|
| mode4 | ko-silence (제거된 모델) | **8,047** |
| mode3 | baseline | 27 |
| mode2 | baseline | 0 |
| mode4 | en-silence-c80 | 0 |

**반복 루프는 ko 모델 전용 현상이었다.** 현재 쓰는 모델 3개 중 2개는 0회.

mode3의 27건이 무엇을 막았는지 확인하니 **전부 정상 발화 오탐**이었다:

```
25건  'Ha!'          ← 낭독체의 실제 웃음 반복
 1건  'Yes.'
 1건  'I hate him.'
```

`Ha! Ha! Ha!`는 LibriSpeech 원문에 실제로 있다. 즉 rep-dedup은 **오탐만 내면서 커서 갭까지 만들고** 있었다.

**조치**: `rep_dedup` 설정 필드 + `--no-rep-dedup` 플래그 신설. **프로덕션 기본값은 ON 유지**(모델이 바뀔 수 있으므로), `serve_mode3.sh`에만 `--no-rep-dedup` 추가.

상한형(`_REP_DEDUP_MAX_REPEATS = 2`, `_collapse_repetition`과 같은 근거)도 만들어 비교했으나 **끄는 쪽이 더 나았다** — 중간에 다른 문장이 끼면 연속 카운터가 리셋돼 실효가 없고, 앞쪽 3개째만 깎아 삭제만 늘었다. 상한형 코드는 남겨 뒀다(루프 모델에서는 여전히 유효).

> ⚠️ mode2/mode4 스크립트에는 **넣지 않았다.**
> - mode2: `always_commit` 분기가 `after=""`로 한 문장만 처리하고 루프를 끝내 `batch_last`가 항상 `None` → **구조적으로 발동 불가**. 플래그가 no-op.
> - mode4: `MODE4_MODEL` 환경변수로 모델을 갈아끼울 수 있다. ko 계열로 되돌리면 8,047회 루프가 그대로 커밋된다. 안전망을 미리 걷어낼 이유가 없다.

## ⚠️ 검증 방법 함정 — 반드시 기억할 것

리팩터링 검증에서 한 번 크게 틀렸다. 문제 파일 149건을 리팩터링 후 코드로 돌려 `concurrent16_dedupfix_run01`(동시 16명, full)과 비교했더니 **35/149 불일치**가 나왔다. 코드 차이로 읽었는데 **러너 차이**였다.

`test_qwen3_librispeech.py`는 챕터 단위로 연결을 재사용해 **앞 발화를 컨텍스트로 쓴다.** `--common-files`로 거르면 30개짜리 챕터가 3개만 남아 컨텍스트가 완전히 달라지고 디코딩 결과도 바뀐다.

이상을 감지한 단서는 **차이의 종류**였다 — `Zawal Makhan`↔`Makan`, `glance, he`↔`glance he` 같은 철자·구두점 변화는 가드가 만들 수 없다. 가드는 커밋 여부만 정하지 단어를 못 바꾼다.

결정적 대조: **동일 코드**로 동시(full) vs 순차(100건 필터링)를 비교하니 8/100 불일치. 확정.

> **규칙: A/B는 파일목록·러너·동시성을 모두 맞춰야 한다.**
> "greedy decoding이라 동시↔순차 출력이 같다"는 판단도 이 오류였다. 대조군 57건이 우연히 컨텍스트에 둔감했을 뿐이다.

## ⏭ 해결되지 않은 작업

- **mode3 full 재측정 미실시.** 위 수치는 증상 파일만 모은 59건(코퍼스의 2.0%, 오디오 2.8%)이라 전체 대표성이 없다. 특히 이 집합은 평균 길이가 코퍼스의 1.4배라 **긴 발화에 편향**돼 있고, 짧은 발화에서 수정이 어떤 부작용을 내는지는 전혀 측정되지 않았다. 커서 조작(④⑤)이 dot 커밋 경로 전반을 건드리므로 2939건 재측정 + 문제파일 149건 회귀 검증이 반드시 필요하다. **논문 수치로 쓰려면 이게 선행되어야 한다.**
- **mode2/mode4는 이 수정들로 재측정 안 함.** 8/4 문서의 최종 비교표는 수정 전 코드 기준이다.
- **`Ha! Ha! Ha!` 3연속 케이스.** rep-dedup을 끈 뒤로는 반대로 5회 커밋된다(삽입 2). 상한형으로도 4회까지밖에 못 줄고 삭제가 늘어 순손해라 방치. `_collapse_repetition`의 `max_repeats=2`도 같은 성질의 오탐을 갖고 있다.
- **mode2/mode4에는 `--no-rep-dedup`을 넣지 않았다.** mode2는 구조적으로 발동 불가라 무의미하고, mode4는 `MODE4_MODEL` 스왑으로 루프 모델이 들어올 수 있어 안전망을 남겼다. 세 모드 설정이 비대칭이라는 점은 기억할 것.
- **`S. J. Severson` 분할.** 단일 대문자 약어가 `_ABBREV_LOOKBEHIND` 목록에 없어 3조각으로 깨진다. 기존 dot 커밋도 동일하게 동작하므로 일관성은 유지되나 개선 여지 있음.
- **정책만 비교하는 실행 미실시.** mode3=baseline vs mode4=en-silence-c80으로 모델이 달라 dot/seg 정책의 순수 효과가 분리되지 않는다.
