작성 2026-09-08. 브랜치 `main`, 커밋 `b6895cc`.

## 2. 다른 서버에서 이어받기

### ① 먼저 확인할 것 — 오디오는 git 에 없다

**DailyTalk 원본 오디오 23,773개(6.9GB, 44.1kHz)가 있어야 한다.** `.gitignore` 로 막혀
있어 클론만으로는 안 된다.

```
Qwen3-ASR/finetuning/data/DailyTalk/audio/{idx}_{화자}_d{대화}.wav
```

git 으로 오는 것은 라벨뿐이다:

| 파일 | 무엇 |
|---|---|
| `transcribe/new_seg_all.json` | 랭크 라벨 원본 `<SEG:n>`. 2,541대화 / 23,773발화 |
| `transcribe/partial_all.json` | 절단 시각. 발화 10,966개(46.1%)의 `end_time` |

`partial_all.json` 이 있어야 절단 창을 만들 수 있다. 없으면 forced aligner(GPU)를 다시
돌려야 하는데, **있으므로 돌릴 필요가 없다.**

### ② 환경

`.venv` 에 아래를 설치했다. `.venv-autoseg` 는 쓸 수 없다 — `peft`·`librosa`·`accelerate` 가
없고 torch 버전도 다르다.

```bash
.venv/bin/pip install peft datasets jiwer tensorboard
```

설치된 것: `peft 0.20.0` / `datasets 5.0.1` / `tensorboard 2.21.0`. `jiwer` 는 이미 있었다.
`transformers 4.57.6` 은 그대로 유지됐다.

> **부작용 하나** — `datasets` 가 `fsspec` 을 2026.7.0 에서 **2026.6.0 으로 내렸다.**
> 같은 venv 를 평가 서버도 쓰므로, 평가 쪽에서 이상이 생기면 이것부터 의심할 것.

`jiwer` 와 `tensorboard` 는 학습 스크립트가 파일 최상단에서 import 하거나 Trainer 가
콜백으로 요구하므로, 쓰지 않더라도 없으면 **즉시 죽는다.**

### ③ 데이터 만들기

```bash
# 1) 랭크 컷 (0.4초, 결정론적)
.venv-autoseg/bin/python evaluation/DailyTalk/utils/rank_to_seg_budget.py -T 2 --min-gap 2

# 2) 창 생성 (약 8분, CPU 전용, LLM·GPU 호출 0)
.venv/bin/python evaluation/DailyTalk/utils/build_windows.py \
  --seg evaluation/DailyTalk/transcribe/new_seg_all_T2_mg2.json \
  --outdir   Qwen3-ASR/finetuning/data/DailyTalk_win \
  --out-audio Qwen3-ASR/finetuning/data/DailyTalk_win/window_audio
```

`--outdir` 을 반드시 `DailyTalk_win` 으로 줄 것. 기본값은 `DailyTalk` 이라 **기존
`train.jsonl`(20,773행)을 덮어쓴다.**

시간의 대부분은 창 wav 4,318개(2.4GB)를 쓰는 데 든다. 원본이 44.1kHz 라 16kHz 로
리샘플하면서 이어붙인다.

### ④ 학습

```bash
tmux new-session -d -s wintrain -c /path/to/STiTy \
  "bash Qwen3-ASR/finetuning/run_win_train.sh"
```

스크립트가 담고 있는 설정:

| 인자 | 값 | 왜 |
|---|---|---|
| `--model_path` | `Qwen/Qwen3-ASR-1.7B` | 베이스에서 출발. 대조군 `en-dailytalk-seg` 와 출발점을 맞춘다 |
| `--batch_size` | 1 | 창이 18.2초라 mel 3000프레임. 기본값 8은 3.4초짜리 기준이라 OOM |
| `--grad_acc` | 24 | 유효 배치 24 → 에폭당 158스텝 |
| `--epochs` | 3 | 총 474스텝 |
| `--save_steps` | 50 | 체크포인트 9개 |

LoRA 는 기본 켜짐(`--use_lora 1`, r=128 / alpha=256)이라 인자를 안 준다. 학습 대상은
380,948,480 / 2,107,836,032 = **18.07%** 다.

**실측 (RTX 4090 24GB, 단일 GPU):**

```
4.19 s/it × 474스텝  =  약 33분
VRAM 11,054 / 24,564 MiB
loss 2.4866 (스텝 10)
```

**VRAM 이 13.5GB 남는다.** `--batch_size` 를 2~4로 올리면 2~3배 빨라진다. 28초짜리 창이
5개 있어 그때 피크가 오므로 여유를 조금 두는 편이 안전하다.

> **받은 자료의 명령을 그대로 쓰면 안 된다.** `torchrun --nproc_per_node=2` 와
> `CUDA_VISIBLE_DEVICES=0,1` 은 GPU 가 2장인 머신 기준이고, `train_split.jsonl` 은
> 8월 24일 1세대 파일로 오디오 경로가 다른 머신(`/home/skkai/...`)을 가리킨다.
> `models/Qwen3-ASR-1.7B` 베이스 가중치도 리포에 없다.

> **오래 도는 작업은 tmux 로 띄운다.** 에이전트 백그라운드 실행은 부모가 죽으면 같이
> 죽는다. 다만 `tmux kill-session` 이 서버 전체를 내린 사례가 있었으니, 다른 세션이
> 떠 있으면 확인하고 죽일 것.

## 3. 왜 이렇게 만들었나

### 이어붙이는 이유는 길이가 아니라 단서다

지금 학습 데이터의 full 행 11,207개는 **전부** "오디오 끝 = `<SEG>`" 다
(`assemble_dailytalk.py` 가 발화마다 끝에 `<SEG>` 를 강제로 붙인다). 그래서 모델이 문장
완결이 아니라 **오디오가 끊기는 것**을 신호로 배울 수 있다.

근거가 리포에 있다 — `results/dailytalk_test_merged{,_pad1s}.json` 은 같은 오디오 뒤에
1초 무음을 붙인 대조쌍인데, **10건 중 2건은 무음을 붙였을 때만 `<SEG>` 가 나온다.**

이어붙이면 창 안쪽의 `<SEG>` 는 뒤에 다음 발화가 바로 이어지므로 그 단서가 없다. 학술
독백에서 필요한 것이 정확히 그 능력이다.

### 창 상한 28초는 특징 추출기가 정한다

`preprocessor_config.json` 이 Whisper 계열이다.

```json
"chunk_length": 30, "n_samples": 480000, "nb_max_frames": 3000
```

**30초에서 오디오가 잘린다.** 넘으면 들리지 않는 뒷부분까지 텍스트 라벨로 주게 되어
할루시네이션을 직접 가르친다. 2초는 리샘플링 오차와 무음 누적분의 여유다.

DailyTalk 은 발화 평균 3.40초, 대화 중앙 8발화(≈29초)라 **대부분의 대화가 28초를 아슬하게
넘겨 두 창으로 쪼개진다.** 그래서 창 평균이 20초 근처에 머문다. 상한을 29초로 올려도 창이
4,172 → 4,045 로 3% 줄 뿐이라, 30초 벽까지 1초만 남기는 위험 대비 이득이 없다.

### 균등 분배 — 평균이 아니라 쪼가리를 없앤다

탐욕적으로 채우면 앞 창을 상한까지 채우고 남은 것을 뒤로 미룬다. 전 대화 실측:

| cap 28초 | 창 수 | 평균 | 5초 미만 |
|---|---|---|---|
| 탐욕 | 4,172 | 19.6초 | **276개** |
| 균등 | 4,120 | 19.9초 | **0개** |

**평균은 거의 안 바뀐다.** 창 평균 길이 = 전체 오디오 ÷ 창 개수인데 균등 분배가 창 개수를
바꾸지 않기 때문이다. 고치는 것은 쪼가리다 — 발화 1~2개짜리 창은 짧은 오디오 끝에
`<SEG>` 가 붙은 모양이라 **지금 데이터와 똑같고, 이 변경의 목적에 정면으로 역행한다.**

### 절단 창 — 반대 신호를 긴 문맥에서 준다

창의 마지막 발화를 문장 중간에서 자르고 끝-`<SEG>` 를 붙이지 않는다. "오디오가 끝나도
커밋하지 마라" 를 가르친다.

기존 `partial` 이 같은 것을 가르쳤지만 **3초짜리 짧은 문맥**에서였다. 실제로 커밋이
무너지는 곳은 문맥이 길어진 뒤이므로, 27초 문맥에 놓는 편이 신호가 정확하다.

절단 시각은 `partial_all.json` 에 이미 있어 aligner 를 다시 돌리지 않는다. **창 경계를
절단 가능한 발화에 맞춰 옮기지는 않는다** — 균등 분배가 깨지고 발화가 버려진다. 그래서
가능한 최대가 43.6% 이고 요청한 50% 에 못 미친다.

### 분할은 대화 단위

`build_splits.py` 는 발화를 무작위로 섞는다. 발화가 독립 샘플일 땐 괜찮았지만, 창은 한
대화의 발화를 묶으므로 그 방식을 쓰면 **같은 창의 발화가 train 과 test 로 갈린다.**
`build_windows.py` 는 대화 단위로 나누되 val/test 목표 크기(각 1,500발화)와 seed 42 는
유지한다. 그래서 분할 멤버십이 종전과 달라 이전 런과의 직접 비교는 제한된다.

## 4. 남은 일 · 알려진 한계

### 이 데이터가 고치지 않는 것

**SEG 사이 최대 텍스트가 158자로 종전(150자)과 같다.** 발화마다 끝-`<SEG>` 를 유지했으니
천장이 안 올라간다.

| | 창 데이터 |
|---|---|
| SEG 사이 조각 | 38,681개 |
| 중앙 | 22자 |
| p99 | 74자 |
| 최대 | **158자** |

측정된 고장은 두 단계인데(5장), 이 데이터는 **진입 빈도만** 낮춘다. 한 번 진입해 미커밋
텍스트가 학습 분포를 벗어나면 회복되지 않는 현상은 그대로다. 그쪽은 런타임에서 다뤄야
한다 — 미커밋 텍스트가 일정 길이(해저드가 무너지는 240자 근처)를 넘으면 강제로 커밋하는
안전망이다. 프로덕션 서버에 `timeout` 커밋 사유가 이미 정의돼 있고 **부르는 데만 없다.**

### 28초를 넘는 창 5개

`pack_equal` 이 평균 무음 0.2초로 계산하는데 실제는 0.1~0.3초 랜덤이라 상한 쪽으로 몰린
창이 넘쳤다. 최대 28.2초로 **30초 벽까지 1.8초 남아 잘리지는 않는다.** 고치려면 무음
상한(0.3초)으로 계산하게 바꾸고 재실행(8분)하면 된다.

### 레지스터는 여전히 대화체다

창 데이터는 문맥 길이와 오디오 끝 단서를 다루지만 **어휘·문체는 그대로 DailyTalk 이다.**
`"Each of these curves represents a different model..."` 같은 학술 문어체는 배우지 못한다.

이게 남으면 다음 후보는 도메인 확장이다. 로컬에 바로 쓸 수 있는 것은
`evaluation/LibriSpeech/LibriSpeech/{dev-clean,dev-other}` 5,567발화(어절 중앙 15~17,
평가는 `test-*` 만 쓰므로 dev 는 깨끗하다). 그 다음은 TEDLIUM-3 같은 강연 코퍼스인데,
**MuST-C 는 배포처가 사라져 쓸 수 없다**([../ast/README.md](../ast/README.md)).

### 커밋 안 한 것

`transcribe/new_seg_all_T2_mg2.json` 은 파생물이라 리포에 두지 않는다 — 위 명령으로
0.4초면 결정론적으로 재생성된다.

## 5. 조사 기록 — 세 가설을 어떻게 기각했나

발표 `2022.acl-long.110`(703초)에서 497초부터 **48.9초** 동안 커밋이 끊겼다. 세 언어에서
48.9 / 49.0 / 48.9 로 거의 같아 번역이 아니라 ASR 쪽 현상이다.

표본은 ACL 6060 dev 5편 × 3언어, 커밋 공백 2,262개
(`results/ACL6060/seg/dev-{de,ja,zh}/20260830_172429`).

### 그 사건은 talk 110 만의 것이 아니다

15초 이상 공백을 언어 중복 제거해 세면 **40건이고 5편 전부에 있다.**

| 발표 | 사건 | 분당 | 최대 |
|---|---|---|---|
| 110 | 11 | 0.94 | **49.0초** |
| 117 | 7 | 0.58 | 37.3초 |
| **268** | **13** | **1.06** | 35.6초 |
| 367 | 6 | 0.52 | 22.2초 |
| 590 | 3 | 0.31 | 21.2초 |

**268 이 110 보다 잦다.** 그리고 공백 분포는 매끄럽다 — p50 4.20 / p90 10.0 / p99 22.17 /
p99.9 45.90 / 최대 49.00초. 표본 2,262개면 p99.9 이상이 2.3개 기대되는데 실제 3개다.
**49초는 별종이 아니라 같은 분포의 최댓값이다.**

종전에 이 구간을 설명하던 "전문 용어를 짧은 템포로 이어 말한다" 는 서사는 원래
**210.6초 결손**(128토큰 교착, `CAP-FREEZE` 로 해결됨)을 설명하려던 것이고, 그 사건이
사라진 뒤 남은 49초에 잘못 상속됐다.

### 가설 1 — 무음이 없어서 · 기각(단서 붙음)

먼저 한 측정이 틀렸다. 파일마다 최대 RMS 의 2%를 무음 임계로 썼는데 발표별 잡음 바닥이
100배 넘게 달라(367 은 0.0134, 111 은 0.0000) 367·590 이 "무음 0회" 로 오검출됐다.
서버가 쓰는 **silero VAD** 로 다시 쟀다.

공백 안쪽을 보면 가설과 **부호가 반대**다. 공백이 길수록 안에 무음이 더 많다(r = +0.388).
30초 넘는 공백 8개는 **전부** 안에 0.8초 이상 무음을 품고 있고, 15초 이상 공백 88개 중
50개(57%)에서 모델은 명백한 휴지를 듣고도 `<SEG>` 를 내지 않았다.

**다만 발표 단위로 정규화하면 방향이 돌아온다:**

| talk | 무음/분 | 사건/분 |
|---|---|---|
| 268 | 0.90 | 1.06 |
| 110 | 2.22 | 0.94 |
| 117 | 3.54 | 0.58 |
| 367 | 3.97 | 0.52 |
| 590 | 5.51 | 0.31 |

순위가 완벽히 뒤집혀 있다 — Spearman **−1.000**, 순열검정 단측 p = 1/120 = 0.0083.
쉼이 적은 화자일수록 SEG 가 자주 침묵한다. n=5 라 근거는 약하다.

정확히 기각된 것은 **"공백 내부 무음 개수로 개별 공백의 길이를 설명할 수 있다"** 까지다.
공백이 길면 포함되는 무음의 기댓값도 자동으로 오르므로, 그 양의 상관을 인과로 읽어서도 안 된다.

### 가설 2 — 128토큰 상한에 걸려 잘렸다 · 기각

잘렸다면 단위 시간당 글자 수가 떨어져야 한다.

| 공백 구간 | 개수 | 방출 글자 | 미커밋 꼬리 | 자/초 |
|---|---|---|---|---|
| 2–5초 | 1,063 | 39.3 | 9.1 | 13.8 |
| 10–15초 | 129 | 148.1 | 13.0 | 13.5 |
| 20–30초 | 32 | 292.0 | 25.8 | 14.3 |
| **30–60초** | 11 | 552.7 | 25.3 | **15.6** |

**전 구간 13~16으로 일정하다.** 48.9초 커밋은 732자 / 14.9자/초로 옛 상한(656자 = 128토큰)을
넘고, 미커밋 꼬리는 0자였다. 잘린 흔적이 없다.

### 가설 3 — 자를 자리가 없었다 · 기각

커밋 텍스트 안의 문장 종결 부호(`. ! ?`) 개수:

| 공백 구간 | 평균 종결 부호 | 2개 이상 |
|---|---|---|
| 2–5초 | 0.47 | 0.2% |
| 10–15초 | 1.07 | 28.7% |
| 20–30초 | 2.72 | 93.8% |
| **30–60초** | **4.64** | **100%** |

20초 넘는 공백 41개 중 종결 부호가 하나도 없던 것은 **단 1개**다. 문제의 49초 커밋에는
마침표가 **7개**, 완결된 문장이 일곱 개 들어 있다. 같은 구간에서 punct 축은 12번 커밋했다.
자를 자리가 없던 게 아니라 **있는 자리를 못 알아본 것**이다.

### 남은 설명 — 두 단계 고장

**진입** — 어느 지점에서 SEG 확률이 문턱 아래로 떨어진다. 대화체로 학습한 신호가 학술
문어체에 반응하지 않는 것으로 본다(소거법이라 직접 확인한 것은 아니다).

**지속** — 일단 미커밋 텍스트가 학습 상한을 넘으면 회복되지 않는다. 학습 라벨의 SEG 사이
조각은 중앙 15자 / p99 69자 / **최대 150자**이고 300자 이상은 0개인데, 문제의 커밋은
**732자**로 4.9배다.

해저드 곡선("이미 t초 지난 공백이 다음 1초 안에 끊길 확률")이 그 지점을 짚는다:

```
 t= 4초  32.2%      t=10초  21.1%
 t= 6초  33.5% ←정점  t=14초  14.9%
 t= 8초  24.2%      t=18초   5.5% ←붕괴
```

무기억(지수분포)이면 평평해야 하고 그 상수는 17.3% 다. 6초(≈80자)에서 정점을 찍고
18초(≈240자)에서 무너진다 — 학습 분포의 p99를 지나 최댓값을 넘어가는 구간이다.
**자기강화 되먹임**이다.

### 이 측정이 말하지 않는 것

- **seg 축이 지고 있다는 뜻이 아니다.** 같은 데이터셋에서 seg 는 static@6s 를 세 언어 모두
  유의하게 이겼다(COMET +0.029 ~ +0.050, 짝지은 부트스트랩). 무너지는 것은 꼬리다.
- 커밋 로그를 뽑은 런은 `no_vad: true` 로 커밋 사유 753개가 전부 `seg` 다. seg 신호를
  정직하게 재려고 바닥을 일부러 껐다. 배포 구성에는 `vad`/`dot`/`timeout` 이 있으므로
  **이 공백은 상한이 아니라 하한이다.**
- 표본은 발표 5편뿐이라 발표 단위 표는 경향으로만 읽어야 한다.
