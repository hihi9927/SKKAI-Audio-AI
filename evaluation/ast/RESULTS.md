### static 곡선을 채웠다 — seg 는 그 위에 있다

static@10s 를 추가하면서 seg 지연(5.1~6.1초) **양옆에 static 점이 생겼다.** 이제
"같은 지연이면 static 은 얼마인가" 를 보간으로 직접 말할 수 있다.

정직하게 쓰면: 두 정책 다 static 곡선 위에 있고, **seg 는 저지연 구간을, punct 는
고품질 구간을 차지한다.** seg 가 punct 를 이긴다는 주장은 이 데이터로 못 한다.

**비용이 seg 의 약점이다.** seg 13.09 호출/분은 punct 의 1.6배, static@10s 의 2.2배다.
품질 +0.03 의 대가가 호출 2.2배라는 점을 반드시 함께 실을 것.

### 평균만 쓰면 seg 를 과소평가한다

static 은 평균과 중앙값이 거의 같다 — 고정 청크라 모든 커밋이 똑같이 기다린다.
**seg 만 1.7초 벌어져 있다.**

```
 축         FTL평균  FTL중앙  차이     중앙→p90
 seg (de)   6.165   4.485   −1.68    3.1배
 static@10s 5.986   5.983    0.00    1.7배
 static@12s 7.100   7.024   −0.08    1.8배
 punct      9.065   8.543   −0.52    1.6배
```

seg 는 문장 절반을 **static@6s 수준(4.5초)으로** 내보내고 소수에서 크게 늦는다.
**seg 의 평균 지연은 꼬리가 만든 값이다**(최대 커밋 공백 48.9초). 체감은 평균보다
중앙값에 가까우므로 **평균·중앙·p90 을 함께 실을 것** — 평균만 쓰면 seg 의 이점이
통째로 가려지고, 중앙만 쓰면 꼬리를 숨긴다.

### 채점기 검산 — static 은 LAAL ≈ 청크/2 여야 한다

static 은 이론값이 닫힌 형태로 나오는 유일한 축이라 하네스 검증용 자석이 된다.

커밋이 고정 격자(6초, 12초, 18초…)에만 일어나므로, 어떤 단위의 음성이 끝난 시각 `t`
는 `t` 이상인 첫 격자점까지 기다린다. 기다림은 `[0, C)` 에 균등하고 평균은 `C/2`.

LAAL 의 `(i−1)·γ` 항이 이걸 보장한다 —

```
d_i − (i−1)γ  =  ⌈t_i/C⌉·C − t_i   (선형 진행분이 상쇄되고 격자 반올림만 남음)
```

실측:

```
축            C/2     de      ja      zh      3언어 평균   차이
static@6s     3.0    3.166   3.293   2.741     3.067     +0.067
static@10s    5.0    5.316   5.439   4.546     5.100     +0.100
static@12s    6.0    6.525   5.878   5.572     5.992     −0.008
```

청크를 6→10→12 로 바꿔도 평균이 0.1초 안에서 따라온다. 언어별로 ±0.5초 흩어지는 것은
γ 가 **균등 발화 속도**를 가정하는데 실제 발화는 균등하지 않아서다(2차 효과).
**이 검산이 깨지면 채점기를 먼저 의심할 것.**

### audio_end 역추적 버그 — 3번 고쳐서 잡았다

**증상.** seg 축에서 커밋의 13.37% 가 음수 지연, 최솟값 −39.5초. 초당 글자수 p90 이
64.1 로 물리적으로 불가능했다.

**원인은 둘이 겹친 것이다.**

*(1) 이미 커밋된 `<SEG>` 가 기록을 다시 채운다.*
`_slot_seg_detected` 는 `"<SEG>" in raw_text` 만 보고 기록한다
([streaming_websocket_server_fsl.py:198](../LibriSpeech/servers/streaming_websocket_server_fsl.py#L198)).
커밋해도 `<SEG>` 는 확정 접두사에 남으므로, 커밋 직후 다음 청크가 **헌 SEG 를 보고**
기록을 다시 만든다. 게다가 `state._seg_token_idx` 는 `on_seg` 안에서만 대입되고
**어디서도 초기화되지 않는다**([qwen3_asr.py:869](../../Qwen3-ASR/qwen_asr/inference/qwen3_asr.py#L869)) —
새 SEG 가 없으면 헌 인덱스가 그대로 남는다.

*(2) `if key not in self._slot_seg_detected` 가 그 뒤로 잠근다.*
한 번 채워지면 다음 커밋의 `pop` 까지 어떤 청크도 못 건드린다.

**그래서 기록은 다음 세그먼트의 *끝* 이 아니라 *시작* 을 가리킨다.**

```
             기록이 가리키는 곳   진짜 끝     오차
 정상 (2초)       502.1          502.4     0.3초   ← 안 보임
 교착 (45초)      502.1          545.6    43.5초   ← 폭발
```

**식도 낡음도 그대로고 커밋 간격만 늘었다.** 그래서 이 버그는 128토큰 교착이 터지기
전까지 몇 달을 숨어 있었다. **audio_end 버그와 CAP-FREEZE 는 같은 사건의 앞뒤다.**

**1차 시도 — 실패.** 상한 감지 시 강제 리셋. 커밋 정책을 바꾸게 되어 폐기.

**2차 시도 — 실패.** `k/n × 2초` 의 2초를 누적 청크량(45초)으로 늘림. `k`·`n` 은
**청크 하나짜리 토큰 수**라 45초 구간에 대한 위치가 아니다. 초당 글자수가 180→488 로
튀고 fsl 이 2.2→15.1초가 됐다.

**3차 — 성공.** 비율을 토큰에서 **글자 수**로 바꿨다. 분모가 누적 구간 전체에 대해
정의되므로 2초든 45초든 똑같이 동작한다.

```
ratio     = len(커밋할 텍스트) / (len(커밋할) + len(남은 미확정))
audio_end = 직전 구간 끝 + ratio × (현재 − 직전 구간 끝)
```

| | 수정 전 | 수정 후 |
|---|---|---|
| 음수율 | 13.37% | **2.86%** |
| 음수 최솟값 | −39.5s | **−4.2s** |
| 초당 글자수 p90 | 64.1 | **18.1** |

**seg 지연 상승분은 전부 이 수정 때문이다.** 번역기 교체(Google→MADLAD)가 NCA 지연에
미친 영향은 0.02초로, 상승분 2.5초와 자릿수가 다르다.

### 번역기 — Google 두 경로가 다 막혔다 (2026-08-31 확인)

```
gtx (무료)   HTTP 429  <title>Sorry...</title>   ← IP 단위 차단 페이지
v2  (유료키) HTTP 403  userRateLimitExceeded     ← 프로젝트 할당량 소진
```

v2 는 20초 간격 단발 요청도 막히므로 속도 제한이 아니라 쿼터 문제다. 키 자체는
유효하다(만료면 400/401). **GCP 콘솔에서 결제·쿼터를 손봐야 풀린다.**

대체로 **MADLAD-400-3B**(greedy, `num_beams=1`, `<2xx>` 접두, 6.75GB VRAM)를 로컬로
띄웠다. 이미 캐시된 대안은 NLLB-200-1.3B / 600M, M2M100-418M 인데 en→de/ja/zh 는
전부 고자원 쌍이라 MADLAD-3B 가 우위다(NLLB 의 강점은 저자원). GPT 는 품질이 낫지만
`GPTTranslator` 가 문맥 창을 쓰므로 **"품질 차이가 분절 정책에서 왔는지 LLM 이 앞
문장을 봐서 왔는지" 를 구분할 수 없게 된다** — 이 논문의 주장과 정면으로 충돌해서 뺐다.

**반복 생성 가드**(`AST_TRANS_ANTI_REPEAT=1`). greedy 디코딩이 같은 4~8자를 4회 이상
반복하는 퇴화를 일으켰고, 특히 ja 에서 음수율을 11.82% 까지 밀어올렸다. 사후에 탐지 →
`repetition_penalty=1.15` 로 재생성 → 그래도 반복이면 절단. 결과 ja 1.63%.

`no_repeat_ngram_size=4` 는 **기각했다** — 정답 참조 자체가 반복 4-gram 을 포함한다
(ja 10.5% / de 6.4% / zh 7.3%). 퇴화 20건 고치려고 정상 73건을 깨뜨린다.

**GPU 설정.** vLLM 이 `gpu_memory_utilization × 24GB` 를 선점하고 MADLAD 활성값이
배치×길이로 자라 OOM 이 났다. `GPU_UTIL=0.5` + `TRANS_BATCH=8` + OOM 시
`empty_cache()` 후 1건씩 재시도로 안정화.

### dot-commit 은 아랍어에서 정상 발동한다 — 참조가 아니라 모델 출력을 봐야 한다

핸드오프의 16 발화 예비 측정을 848 전체로 확인했다. **결론이 유지된다.**

| | `.` | `،` | `؟` | `:` | `!` | 종결부호로 끝난 발화 |
|---|---|---|---|---|---|---|
| Casablanca 참조 | 2 | 249 | 122 | 1 | 137 | — |
| Casablanca 모델 출력 | **728** | 108 | 97 | 0 | 0 | 767/848 (90.4%) |
| FLEURS 참조 | 323 | 242 | 1 | 15 | 1 | — |
| FLEURS 모델 출력 | **320** | 172 | 0 | 2 | 0 | 283/283 (100%) |

참조는 ASCII 마침표를 사실상 안 쓰지만(848행 중 2회) **모델은 728회 찍는다.** dot-commit 을
굴리는 것은 참조가 아니라 모델 출력이므로, "아랍어는 `.` 을 안 쓰니 dot-commit 이 죽는다"는
추론은 틀렸다. 아랍어에서도 정상 발동한다.

### `؟` 패치 효과 — 구어에서만 유의미하다

`sentence_boundary.py` / `streaming_websocket_server_dualbase.py` 에 `؟`(U+061F)·`۔`(U+06D4)를
추가한 효과를 위 가설 출력에 그대로 재보면:

| | dot-commit 경계 패치 전 | 패치 후 | 증가 |
|---|---|---|---|
| Casablanca 요르단 | 727 | 824 | **+97 (+13.3%)** |
| FLEURS `ar_eg` | 315 | 315 | +0 |

Casablanca 에서 **69 발화(8.1%)가 `؟` 로 끝난다.** 패치 전에는 이들이 dot-commit 으로
나가지 못하고 finish/timeout 커밋으로 밀렸다. MSA 에서는 모델이 `؟` 를 아예 안 찍어
효과가 0 이다.

즉 핸드오프가 "우선순위 낮음"으로 본 것보다 **회화체에서는 값이 크다.** 반대로 MSA 낭독체만
다룬다면 없어도 된다. 패치는 적용했다(커밋 `1bae6fc`) — 라틴/CJK/약어(`Mr.`)/소수점(3.14)
회귀 없음을 확인했다.

### 아랍어 AST 지연 — FLEURS ar_eg→en, 2026-08-31

WER 측정(위 절)은 오프라인 배치라 지연이 안 나온다. 스트리밍 서버로 다시 돌린 결과다.

**왜 FLEURS 인가.** Casablanca 는 `tgt_text` 가 비어 있어 `metrics_ast.py:141` 이 `n_ref=None`
을 넘기고 `:117` 에서 분모가 `max(n_hyp, 0)` = `|Y_hyp|` 가 된다 — **LAAL 이 조용히 AL 로
바뀌어** 짧게 생성할수록 지연이 작아 보이는 구멍이 열린다. FLEURS 는 n-way 병렬이라
ar_eg 음성 + en_us 참조로 진짜 LAAL 이 나온다.

**dot-commit 은 아랍어에서 실제로 발동한다 — 스트리밍으로 확인했다.** 커밋 324건이 전부
`dot` 이고 발화당 1.15건이다. FLEURS 는 발화가 대체로 한 문장이라 문장 끝에서 한 번 터지고,
그래서 지연 10.41초가 평균 오디오 길이 11.14초에 거의 붙는다 — **"문장이 끝날 때까지 기다린다"**
는 뜻이다. 영어 punct(en→de 9.044초)와 같은 대역이라 아랍어라서 느린 것은 아니다.

**문제는 중간이 비었다는 것이다.** 지금 아랍어가 고를 수 있는 점은 두 극단뿐이다.

```
static@2s   1.1초 / BLEU  8.55   ← 빠르지만 못 쓴다 (11초 발화를 2초로 자르면 단어 중간에서 끊긴다)
punct      10.4초 / BLEU 34.70   ← 쓸 만하지만 사실상 문장 단위 대기
```

en→de/ja/zh 표에서 이 사이를 메우는 것이 **seg 축**이다(en 기준 6.075초에 COMET 최고 0.7171).
**아랍어에는 그 점을 찍을 수 없다** — 베이스 모델은 `<SEG>` 를 뱉지 않고, `en-dailytalk-seg` 는
영어 파인튜닝이라 아랍어에 못 쓴다. **아랍어를 실시간으로 쓰려면 아랍어 SEG 파인튜닝이
선결 과제다.** static 청크를 6~12초로 키우면 BLEU 는 오르지만 그건 지연을 punct 쪽으로
되돌리는 것이라 중간 점이 되지 못한다(en 표의 static@10s·@12s 가 그 증거다).

**이 런은 `؟` 패치를 검증하지 못한다.** FLEURS ar_eg 모델 출력에 `؟` 가 0건이라(위 부호 분포
표) 패치가 걸릴 자리가 없었다. `؟` 가 나오는 것은 Casablanca 구어인데 거기서는 LAAL 이
성립하지 않는다. 패치의 +13.3% 는 여전히 **출력 텍스트에 정규식을 다시 돌린 정적 추정**이지
실측 커밋 타이밍이 아니다.

**스모크(8발화)의 CA 42.6초는 artifact 다.** 16클라이언트가 동시에 출발하는데 그때 MADLAD 가

### 재현

`HANDOFF_arabic.md` 재현 절차와 두 가지가 다르다.

- **환경**: 이 머신(`skkai`)에는 `speech_ai` conda env 가 없다. `PYTHONPATH= .venv/bin/python`
  으로 실행한다(ROS PYTHONPATH 간섭 때문에 비우는 것이 필수).
- **`gpu_memory_utilization`**: 핸드오프의 `0.2` 는 GB10(통합메모리 121GB, 0.2≈24GB) 기준이다.
  24GB 4090 에서 0.2 는 4.9GB 로 1.7B fp16(3.87GB) + KV 에 모자란다. **0.7 을 쓴다**(KV 11.46GB).

```bash
PYTHONPATH= .venv/bin/python evaluation/ast/build_manifest_casablanca.py \
    --casablanca-root ~/datasets/casablanca --dialect Jordan --split test \
    --out evaluation/ast/manifests/casablanca_jordan_test.jsonl

PYTHONPATH= .venv/bin/python evaluation/ast/build_manifest_fleurs.py \
    --fleurs-root ~/datasets/fleurs --src ar_eg --tgt ar_eg --split test \
    --out evaluation/ast/manifests/fleurs_ar_test.jsonl

for m in casablanca_jordan_test fleurs_ar_test; do
  PYTHONPATH= .venv/bin/python evaluation/ast/asr_eval_arabic.py \
      --manifest evaluation/ast/manifests/$m.jsonl \
      --out evaluation/ast/results/asr_ar/$m.json \
      --batch-size 32 --backend-kwargs '{"gpu_memory_utilization": 0.7}'
done
```

추론은 각각 17초 / 13초다(모델 로드 제외). 핸드오프의 "transformers 백엔드는 7.4시간" 경고는
vLLM 기본값을 쓰는 한 해당 없다.

**FLEURS TSV 따옴표 버그는 `ar_eg` 에 해당하지 않는다.** 기본 파싱과 `QUOTE_NONE` 이 둘 다
428행으로 같고, 3행이 리터럴 `"` 유지 여부만 다르다(행 삼킴 없음). 따라서
`build_manifest_fleurs.py` 는 손대지 않았다 — 수정하면 기존 AST 매니페스트가 바뀌므로
여전히 사용자 판단 대기다.

## NCA vs CA — 둘을 함께 실어야 하는 이유 (결론은 2026-08-31 에 뒤집혔다)

> **⚠ 수치도 결론도 무효.** NCA/CA 의 정의와 "둘을 함께 실어야 한다"는 원칙만
> 유효하다. **"seg 만 CA 가 폭발한다"는 결론은 개정 후 사라졌다** (ja 기준):
>
> ```
>              CA − NCA
> 축          08-28   08-31
> static@6s   0.221s  1.102s
> seg         3.286s  1.069s   ← 더 이상 이상치가 아니다
> punct       0.272s  0.711s
> ```
>
> 두 가지가 동시에 움직여서 어느 쪽 기여인지 깨끗이 못 가른다 — (1) audio_end
> 수정이 seg 의 NCA 를 뒤로 밀었고, (2) 번역기가 Google API → 로컬 MADLAD 로
> 바뀌면서 **전 축이 약 1초의 계산 비용을 새로 얹었다.** 옛 표의 "seg 만
> `asyncio.create_task` 로 발사돼 격차가 5.5배" 라는 설명은 재검증이 필요하다.

LAAL 의 `d_i` 를 무엇으로 세느냐가 둘로 갈린다.

| | `d` 의 정의 | 무엇을 재나 |
|---|---|---|
| **NCA** (주지표) | 커밋을 결정한 순간까지 읽은 소스 오디오 | **정책만.** GPU 가 달라도 재현된다 |
| **CA** | 클라이언트가 `final` 을 실제로 받은 경과 시각 | **사람이 기다린 시간.** 추론·번역 왕복 포함 |

`CA − NCA` 가 곧 계산 비용이다. 세그먼트별 FSL 평균과 대조해 검산했다(ja 기준):

```
데이터셋    축          NCA      CA     격차    평균FSL
CoVoST2   static      1.311s  1.554s  0.242s   0.207s
CoVoST2   seg         2.762s  3.355s  0.594s   0.500s
CoVoST2   punct       4.518s  4.756s  0.239s   0.594s
ACL       static      1.512s  1.733s  0.221s   0.251s
ACL       static@4s   2.178s  2.469s  0.291s   0.324s
ACL       seg         2.806s  6.092s  3.286s   1.903s   ←
ACL       static@6s   3.211s  3.575s  0.364s   0.366s
ACL       punct       8.174s  8.446s  0.272s   0.844s
```

**seg 만 장문에서 격차가 폭발한다**(0.594s → 3.286s, 5.5배). 다른 축은 두 데이터셋에서
0.2~0.4초로 같다. `<SEG>` 커밋만 `asyncio.create_task` 로 발사되고 나머지는 직접 `await`
하기 때문이다 — 번역이 다음 청크 처리와 겹쳐 돌아 결과가 늦게 나간다. 장문은 청크마다
누적 오디오 전체를 다시 듣느라 청크 처리가 느려(0.3~0.7초) 그 지연이 크게 누적된다.

그래서 결론이 하나 더 붙는다:

```
NCA 기준   seg 2.806s  <  static@6s 3.211s   → seg 승
CA  기준   seg 6.092s  >  static@6s 3.575s   → seg 패 (2.5초 차)
```

**정책으로서는 seg 가 낫지만, 현재 구현으로 서비스하면 체감 지연은 seg 가 제일 나쁘다.**
두 값을 반드시 같이 실을 것 — NCA 만 쓰면 seg 를 과대평가하고, CA 만 쓰면 정책 비교가
GPU 성능에 오염된다. 이 격차는 정책의 성질이 아니라 **구현 문제**일 가능성이 크므로
"현재 구현에서는" 이라는 단서를 달아 쓴다.

## FTL — 장문에서는 문장 단위로 재야 한다

> **⚠ 표의 수치는 무효.** 개정 절의 FTL 평균/중앙/p90 을 볼 것.
> "발표 단위 FTL 은 못 쓴다", "p90 을 함께 실어라", "음수를 0으로 자르지 마라"는
> 결론은 그대로 유효하다.

**발표 단위 FTL 은 못 쓴다.** 클라이언트가 재는 값은 12분짜리 발화의 **첫 커밋 하나**만
보므로 발표당 표본이 1개다(5발표 → 5표본). 발표 도입부가 어땠냐에 좌우된다.

문장 단위 FTL = 재분절된 참조 문장마다 `d_1 − 문장 시작 시각`. StreamLAAL 이 평균 내는
재료의 **첫 항**과 같다. 468문장이라 분포를 볼 수 있다. `score_acl6060.py` 가
`ftl_sec` / `ftl_ca_sec` 로 낸다(평균·중앙·p90·음수 개수).

| 축 | lang | FTL 평균 | 중앙 | **p90** | 음수/468 | FTL_CA 평균 | FTL_CA p90 |
|---|---|---|---|---|---|---|---|
| static@2s | ja | 1.414s | 1.453s | 3.452s | 83 | 1.632s | 3.683s |
| static@4s | ja | 2.042s | 2.202s | 4.607s | 75 | 2.326s | 4.898s |
| **seg** | ja | **2.988s** | 2.671s | **9.047s** | **114** | 5.595s | 12.686s |
| static@6s | ja | 3.171s | 3.241s | **6.208s** | 49 | 3.495s | 6.522s |
| punct | ja | 7.343s | 7.369s | 13.101s | 9 | 7.626s | 13.440s |

**평균만 보면 seg 가 static@6s 를 이기지만, p90 에서 진다.**

```
ja 평균   seg 2.988s  <  static@6s 3.171s     → seg 승
ja  p90   seg 9.047s  >  static@6s 6.208s     → seg 패 (2.8초 차)
```

seg 는 대체로 빠르지만 **SEG 가뭄에서 크게 늦는 꼬리**가 있다(최대 커밋 공백 49.6초).
static 은 2초마다 무조건 커밋하니 꼬리가 짧다. **p90 을 반드시 함께 실을 것** —
평균만 쓰면 유리한 쪽만 보여주는 셈이다.

seg 는 468문장 중 114개(24%)에서 FTL 이 **음수**다. 재분절이 앞 커밋 텍스트를 그 문장에
배정해서다. 즉 seg 의 FTL 평균 2.988초도 음수가 끌어내린 값이다. **음수를 0으로 자르지
않는다** — 자르면 재분절 오배정이 정시로 위장된다.

### 128토큰 교착 — 이 결과를 내기 전에 고쳐야 했던 것

첫 dev 런(`20260827_133539`)은 **seg/ja StreamLAAL 이 −1.859초**로 나왔다. 물리적으로
불가능한 값이라 원인을 끝까지 팠다.

**증상.** 발표 `2022.acl-long.110`(703.0초)에서 seg 축의 마지막 커밋이 492.4초였다.
뒤 **210.6초가 통째로 유실**됐고 `finish` 커밋도 `finish_done` 도 없었다. de/ja/zh
세 언어 + 단독 재현까지 **4회 모두 492.4초로 동일** — 결정적 현상이었다.

**원인.** 서버는 마지막 `<SEG>` 까지만 prefix 로 굳히고 그 뒤는 매 청크 통째로 다시
생성한다(`_build_streaming_prefix`). 커밋이 멈추면 그 재생성 구간이 초당 약 3토큰씩
자라 **약 43초면 `max_new_tokens=128` 에 닿는다**. 잘리는 위치가 텍스트 기준이라
시간이 지나도 같은 자리에서 시작해 같은 128토큰을 만들고 같은 자리에서 잘린다.
그 뒤에 있을 `<SEG>` 는 생성 자체가 안 되므로 커밋이 영원히 안 난다.

실측: **130청크 연속 완전히 같은 656자**(=128토큰, `"…prefix length. However"` 에서
문장 중간 절단). 오디오를 260초 더 들었는데 출력이 한 글자도 안 변했다.

**방아쇠는 오디오, 자물쇠는 하네스.** 492~560초 구간은 0.5초 넘는 휴지가 68초에
단 1번뿐인 조밀한 그래프 설명 대목이다. 그 구간만 잘라 **빈 맥락에서** 넣으면 SEG 가
25.2초 만에 돌아오고 상한에 닿지도 않는다(대조군 정상 구간 15.7초). 즉 내용은
25초짜리 흔한 사건을 만들고, 210초로 키운 것은 하네스다.

같은 오디오에서 **punct 는 같은 구간에 12번 커밋했다.** 마침표는 정상적으로 나왔고
ASR 전사도 멀쩡했다. `<SEG>` 신호만 안 나온 것이다 — DailyTalk(짧은 대화)로 파인튜닝한
SEG 가 학술 독백에서 일반화되지 않는다는 뜻이고, 이건 고칠 게 아니라 보고할 내용이다.

**수정(`_ast_install_cap_freeze`, `streaming_websocket_server_ast.py`).** 생성이 상한에서
잘렸다는 사실은 추측이 아니라 확정 신호다(`state._last_chunk_new_tokens >= max_new_tokens`).
그 시점부터 한시 모드로 들어가 매 청크 `end_idx = len(cur_ids) - unfixed_token_num` 으로
커서를 굴린다. **커밋 정책은 건드리지 않는다** — 바뀌는 것은 모델이 다시 만들지 않는
범위(`_prefix_end_idx`)뿐이고, `final` 은 여전히 `<SEG>` 에서만 나간다. 그래서 이 수정
뒤의 숫자는 "정책을 바꾼 결과" 가 아니라 seg 정책의 정직한 성능이다.

**기본은 꺼짐.** `AST_CAP_FREEZE=1` 로 띄울 때만 설치된다. 끄면 base 와 동일 동작이라
롤백은 환경변수를 빼는 것으로 끝나고, 이전 CoVoST2 결과와도 그대로 비교된다.
벤더 코드(`Qwen3-ASR/`)는 건드리지 않고 런타임에 클래스 메서드만 교체한다.

### 음수 지연은 seg 정책의 성질이다 — 반드시 함께 보고할 것

수정 후에도 seg 의 음수 지연 비율은 높다(ja 기준):

```
축          음수 / 단위        비율
punct         10 / 23,498     0.04%
static@6s    125 / 21,983     0.6%
static@2s    465 / 22,878     2.0%
seg        1,546 / 22,947     6.7%
```

음수는 "그 참조 문장의 음성이 시작되기 전에 번역이 나갔다"는 뜻이라 실제로는 **글자가
다른 문장에 배정됐다**는 신호다. punct 는 커밋 단위가 곧 문장이라 경계에서 한두 글자만
샌다(중앙 −0.9초, 최악 −2.6초). seg 는 의미 단위가 참조 문장 여러 개에 걸치므로
문장 하나가 통째로 음수가 되기도 한다(중앙 −3.2초, 최악 −39.5초 = 최대 커밋 공백 크기).

**따라서 seg 의 StreamLAAL 은 음수가 평균을 끌어내린 값이다.** 액면 그대로 축 간
비교하면 seg 가 실제보다 빨라 보인다. 표에 음수율 열을 반드시 함께 넣을 것.

수정 전의 −207초는 성질이 아니라 **정렬 붕괴**였다(210초 공백을 재분절이 메우려다
앞 텍스트를 뒤 문장에 배정). 지금의 −39.5초는 사실의 정직한 반영이다.

`조각내부위반 0` / `경계역전 0` — 어댑터는 전 축·전 언어에서 깨끗하다.

- **punct 의 ASR WER 언어간 편차 1.45%p** 원인 미확인(다른 축은 0.1 이내).
- `run_covost2.sh` 헤더가 `번역 : Cloud Translation v2` 를 하드코딩해 찍는다. 실제로는
  `TRANS_BACKEND` 를 따른다(서버 로그의 `[TRANS-GUARD] 로컬 번역기 로드` 가 진실).
  런이 도는 중이라 못 고쳤다 — 끝나고 고칠 것.
- 발표가 5편뿐이라 신뢰구간은 **문장 단위** 복원추출이다(발표 단위가 아니다).

- `[CAP-FREEZE]` 해제 경로 중 슬롯 리셋으로 나가는 쪽에 로그가 없어 **굳어 있던 지속
  시간을 못 잰다**(진입 3 / 해제 0 으로 찍힌 이유). 지표에는 영향 없다.

### 어떻게 읽을 것인가

CoVoST2 단클립은 평균 4.27초의 **거의 한 문장**이다. 여기엔 의미 분절이 찾을 문장 중간
경계가 별로 없는데, seg 는 발화당 1.89회 커밋한다 — 필요 이상으로 자르면서 품질만 잃고
지연 이득은 못 얻는다. 반대로 4초 청크는 이 길이대에서 우연히 "거의 발화당 1회"가 되어
잘 맞아떨어진다.

즉 **"이 데이터셋에서는 의미 분절이 할 일이 없다"** 는 결과다. 방법이 틀렸다는 결론은
아직 아니지만, **CoVoST2 만으로는 주장을 세울 수 없다.** 문장이 연속으로 이어지고 고정
청크가 경계를 맞출 수 없는 **장문(ACL 60/60)** 이 이제 선택이 아니라 필수다.

무관**하다. 배선 검산으로도 쓸 수 있다.

나눠 가질 뿐이라 총 글자 수가 거의 같다. 다만 두 경우에 곧바로 비용이 된다:

1. **LLM 번역(`--gpt-translation`)** — 호출마다 시스템 프롬프트·문맥이 새로 들어가므로
   고정 오버헤드가 호출 수에 비례한다. static 은 punct 의 2.35배를 낸다.
2. **동시 사용자** — 100명 기준 초당 호출 static 58.9 / seg 44.3 / punct 25.1.
   무료 gtx 가 막힌 축이 정확히 이것이다.

즉 call count 는 "이번 청구서"가 아니라 **정책의 구조적 비용**으로 읽어야 한다.
seg 는 punct 의 1.76배 호출로 지연을 35% 줄인다.

### LAAL 을 읽는 법 — 뺄셈 항이 축마다 다르다

`LAAL = (1/τ)·Σ[d_i − (i−1)·γ]`, `γ = T/max(|Y_hyp|,|Y_ref|)`. 뺄셈 항은 "소스를 균일한
속도로 따라가는 이상적 시스템" 기준선이고, **i 는 세그먼트가 아니라 타깃 단어를 센다.**
en→de 실측 분해:

| 축 | 평균 d_i (실제 지연) | 뺄셈 항 | LAAL | τ 평균 |
|---|---|---|---|---|
| static | 2,817 ms | −1,580 ms | **1,237 ms** | 8.52 |
| seg | 3,471 ms | −826 ms | **2,645 ms** | 4.45 |
| punct | 4,186 ms | −125 ms | **4,061 ms** | 1.35 |

static 의 LAAL(1.24초)이 청크 크기(2초)보다 작은 이유가 이것이다. 일찍 커밋을 시작하면
T 도달 전에 타깃 단어가 많이 나가고(τ=8.52) 기준선 대비 크레딧을 크게 받는다. **static 의
실제 평균 지연은 2.8초다.** 사용자 체감 대기는 LAAL 이 아니라 FTL 로 봐야 한다.

### punct 는 이 데이터셋에서 스트리밍 정책이 아니다

| 축 | 첫 커밋 d₁ | 발화 길이 T | **d₁/T** | 커밋 1개뿐인 발화 |
|---|---|---|---|---|
| static | 1.96 s | 4.27 s | 0.56 | 12% |
| seg | 3.20 s | 4.27 s | 0.81 | 42% |
| punct | 4.18 s | 4.27 s | **0.99** | **93%** |

CoVoST2 단클립은 대부분 한 문장이라 마침표가 끝에만 있다. punct 는 발화의 99% 지점에서
처음 커밋하고 93% 가 단일 커밋이다 — **사실상 오프라인 번역**이다. 따라서

- punct 의 BLEU 33.47 / WER 7.57% 는 경쟁 baseline 이 아니라 **오프라인 상한선**이다.
- "seg 가 punct 보다 6.53 BLEU 낮다"는 "스트리밍이 오프라인보다 6.53 낮다"로 읽어야 한다.
- 진짜 스트리밍끼리의 비교는 **static vs seg** 이고, 여기서 seg 가 +10.21 BLEU /
  +0.135 COMET 로 앞선다(지연은 2배).
- seg 는 d₁/T = 0.81, **58% 의 발화에서 문장 중간을 실제로 분절**한다.

이것이 ACL 60/60 장문이 필요한 이유다 — 10분짜리 발표에서는 punct 가 문장마다 발동해
비로소 스트리밍 baseline 이 된다.

| `regime_covost2` | 좌: 첫 커밋 시점 / 발화 길이(= 얼마나 오프라인인가), 우: 커밋 빈도 대 ASR WER |

### 반드시 같이 보고할 것 — 축마다 ASR 품질이 다르다

| 축 | 커밋/발화 | **ASR WER** | seg 축과 전사가 같은 발화 |
|---|---|---|---|
| static | 2.52 | **26.40%** | 33.6% |
| seg | 1.89 | **13.80%** | — |
| punct | 1.07 | **7.57%** | 75.8% |

WER 이 커밋 빈도를 정확히 따라간다. 커밋된 텍스트는 이후 디코딩의 **고정 접두사**가 되어
수정될 수 없고(`committed_token_len`, 롤백 금지), 잘린 뒤의 오디오는 앞 문맥 없이 따로
디코딩된다. 실례(static, 2.5초 발화):

```
정답 : Tell Nathan to get on the extension.
ASR  : Tell Nathan to get on the extension Trin.
   청크1 커밋 → 'Tell Nathan to get on the extension'   ← 문장 중간에서 확정
   청크2 커밋 → 'Trin.'                                  ← 남은 0.5초를 따로 디코딩
```

**따라서 BLEU/COMET 차이는 "분절 품질"과 "ASR 품질"을 섞고 있다.** 이건 버그가 아니라
스트리밍 커밋의 본질이다 — 정책이 곧 ASR 에게 몇 번의 수정 기회를 줄지 정한다. 분리할 수
없으므로 WER 을 함께 보고해야 한다. 안 그러면 seg 의 BLEU 열위를 분절 탓으로만 읽게 된다.

### 축 오염 — 같은 가중치로 세 축을 돌릴 때의 함정

dailytalk-seg 는 축과 무관하게 `<SEG>` 를 생성한다. 두 가지가 샜다.

1. base 는 커밋 구간에 `<SEG>` 가 섞이면 `trigger = "seg" if "<SEG>" in matched_text`
   로 라벨을 바꾸고, 그 순간 `if trigger == "dot" and self.dot_commit_confirm` 의
   **확정 게이트를 건너뛴다.** 실측(20발화 punct 축): `{'dot': 21, 'seg': 12}` — 36% 가
   확정 없이 즉시 커밋됐다.
2. FSL 은 `"<SEG>" in state.text` 만 보고 `_slot_seg_detected` 를 채우므로, dot 커밋에
   SEG 감지 시점이 `decisionAudioSec` 로 새어 든다.

**생성을 막는 것은 해법이 아니다.** vLLM `bad_words=["<SEG>"]` 로 막았더니 그 자리
확률 질량이 차선 토큰으로 흘러 `icky` 같은 무의미한 단어가 끼어들었다:

| 축 | SEG 차단 | ASR WER | `icky` 삽입 |
|---|---|---|---|
| seg | 안 함 | 9.26% | 0회 |
| punct | 함 | 11.73% | 12회 / 7발화 |
| static | 함 | 29.63% | 18회 / 10발화 |

해법은 `parse_asr_output` 을 감싸 **서버가 받는 텍스트에서만** `<SEG>` 를 지우는 것이다
(`ASTStreamingServer._ast_hide_seg_token`). 디코딩·프리픽스 재조립은 `state._raw_decoded`
를 쓰므로 생성은 그대로다. 이 한 지점이 `state.text`, `on_seg` 콜백(`txt_p.count("<SEG>")`
로 발동), 커밋 trigger 판정을 모두 덮는다.

### 번역 백엔드 — 무료 gtx 는 못 쓴다

`translate.googleapis.com/.../single?client=gtx` 는 브라우저 위젯용 비공개 엔드포인트다.
인증이 없어 Google 이 구분할 수 있는 건 IP 뿐이고, **2026-08-18~23 에 분절 실험이
299,168 건을 호출한 뒤 이 IP 가 429("Sorry..." HTML)로 막혔다.** 이 실험 하나만도
주표 기준 17,015 호출이라 같은 규모다 — 차단이 풀려도 재현되지 않는다.

공식 **Cloud Translation Basic(v2)** 로 옮겼다(`--trans-backend v2`, `.env` 의
`GOOGLE_TRANSLATE_API_KEY`). 요금은 백만 자당 $20, 매달 50만 자 무료. 이 런의 소스
글자수는 약 1.4M 자다.

프로덕션의 `google_translate_async` 는 **예외를 삼키고 `("", "")` 를 돌려준다.** 차단되면
"번역이 빈 커밋"이 되어 정책이 아무 말도 못 만든 경우와 구분되지 않는다. 그래서 평가
서버에는 재시도·백오프·계측을 붙였다(`ast/trans_guard.py`). 이 런의 실측:

```
커밋 17,015 / 호출 17,133 / 재시도 118 / 실패 2 (0.012%)
오류: JSONDecodeError 72, TimeoutError 48   ← 전부 재시도로 흡수됨
```

### 소요

9런(3축 × 3언어) 약 5시간. 서버 기동은 축당 25초(3회), 처리 8.7배속(16병렬).
